PART ONE

地基

在讨论比特币之前，我们需要三样工具：一个"改不动"的数据结构，一个"单向"的函数，以及一种"只有主人能签、所有人都能验"的签名方式。这三样东西都不是比特币发明的，但比特币把它们拼在了一起。

Chapter 01从"记账"说起

比特币的本质不是"币"，而是一本账。理解账本，比理解币重要得多。

1.1 一个村子里的转账问题

假设 Alice 想给 Bob 转 10 块钱。在没有银行、没有货币系统的原始状态下，最直接的做法是 Alice 写一张欠条给 Bob：

欠条plain
我，Alice，欠 Bob 10 元。
                                    —— Alice

这个方案立刻暴露三个问题：

  1. 伪造：任何人都可以写一张"我是 Alice，我欠 Bob 10 元"。
  2. 重复支付：Alice 只有 10 块钱，却同时给 Bob、Carol、Dave 各写了一张欠条。
  3. 核实成本：Bob 收到欠条后，怎么知道 Alice 现在到底还有多少钱？他得去问所有人。

问题 2 有个专门的名字，叫 双重支付（double spending），它是所有电子货币必须解决的第一难题。 注意，这不是密码学问题，是记账顺序问题——只要能把"谁先花"这件事定下来，双重支付就不存在了。

1.2 解决方案一：中心化账本

银行的做法是：把所有人的欠条撕掉，改成一本统一的账。账本只有一本，由银行保管。转账时，银行在账本上做两条记录：

时间账户变动余额
09:00Alice−1090
09:00Bob+10130

这个方案极其高效：没有伪造（银行盖章才算数），没有双重支付（余额由银行一处维护）。 但它有一个根本性的代价——你必须信任银行。信任它不会偷偷改数字，信任它不会冻结你的账户， 信任它不会因为破产、战争或政策而关门。

历史上，人类绝大部分时间选择了"信任中心"，因为替代方案的成本高得离谱。比特币的意义在于它第一次给出了一个可行的替代方案。

1.3 解决方案二：分布式账本，以及它的致命问题

换一个思路：如果每个人手里都有一份完整的账本副本呢？Alice 转账时，向全网广播一条消息：

广播消息plain
Alice 转给 Bob 10 元（Alice 签名）

每个人收到后，把这条记录追加到自己的账本末尾。听起来很美好，但立刻会遇到三个新问题：

问题具体表现
谁有权写入任何人都能广播"我从 Alice 账户转走 100 万"，凭什么接受？
顺序怎么定Alice 同时广播"转 Bob 10 元"和"转 Carol 10 元"，但账户只有 10 元。不同节点收到的顺序可能不同，账本就不一致了。
如何防篡改我有账本副本，我偷偷改掉其中一条记录，别人怎么发现？

这三个问题在计算机科学里有个经典的名字：拜占庭将军问题（Byzantine Generals Problem）。

拜占庭将军问题

几支军队包围一座城，必须同时进攻才能取胜。将军之间只能靠信使通信，而信使可能被杀，将军中可能有叛徒。问题是：如何让忠诚的将军达成一致的进攻时间？

对应到账本：将军 = 节点，信使 = 网络，叛徒 = 恶意节点。在存在叛徒的前提下达成一致，就是共识问题。

1.4 比特币的三层答案

比特币对上述三个问题的回答，构成了全书的主干：

问题比特币的答案用到什么章节
谁有权写入想写就得付出算力成本，成本与"记账权"挂钩工作量证明第 10 章
顺序怎么定把所有记录打包成区块，串成一条链，链的顺序就是账的顺序哈希链第 4 章
如何防篡改改动任何一条旧记录，会导致后面所有区块的哈希全部失效，需要重做全部算力哈希函数的单向性第 2 章
怎么证明是本人授权只有私钥持有者能生成有效签名，但任何人都能验证ECDSA 数字签名第 3 章
核心认知

比特币没有"币"这个东西。账本上只有记录，没有币。"你持有 1 个比特币"这句话，精确的表述是："账本上存在若干条记录，它们规定了这些钱只能由你的私钥来花费。"

理解这一点，第 5 章的 UTXO 模型就顺理成章了。

1.5 一个必须先破除的误解

很多人以为比特币"匿名"，所以适合干坏事。事实正相反：比特币是全世界最透明的账本。 每一笔交易、每一个地址的余额、每一笔资金的完整流向，都公开可查，永久保存，任何人可以用浏览器查。

它保护的是身份与地址之间的关联（伪匿名），而不是交易本身。一旦某个地址被关联到现实身份， 这个地址的全部历史、以及所有与它发生过交易的地址，都会被一起暴露。第 20 章会详细讲这件事。

本章要点
  • 比特币的本质是账本，不是币；核心难题是在互不信任的节点间对账本达成一致。
  • 中心化账本高效但需要信任；分布式账本无需信任，但要解决"谁写、什么顺序、怎么防篡改"。
  • 比特币用哈希链定顺序、签名定授权、工作量证明定写入权，三者缺一不可。
  • 比特币不是匿名，而是伪匿名 + 完全公开的账本。

Chapter 02哈希：一把单向的锁

如果只能选一个概念来理解比特币，那就是哈希函数。整个系统的"不可篡改"完全建立在它之上。

2.1 什么是哈希函数

哈希函数做的事非常简单：把任意长度的输入，压缩成固定长度的输出。 比特币用的是 SHA-256，无论你输入一个字母还是整部《战争与和平》， 输出永远是 256 位，也就是 64 个十六进制字符。

demo_hash.pypython
import hashlib

def sha256(b):
    return hashlib.sha256(b).hexdigest()

print(sha256(b"hello"))
print(sha256(b"hellp"))   # 只把 o 改成了 p

运行结果（你可以自己跑一遍验证）：

输出text
2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
fdd7585e08c4e2afd71dcabdb4636c89d557a3f42db9e2040c8bbd1708aa4ce7

输入只差一个字母，输出却面目全非。这不是巧合，而是精心设计的结果。

2.2 好哈希函数的四个性质

① 确定性（Deterministic）

同一个输入，永远得到同一个输出。无论在什么机器上、什么时间、运行多少次。这一条保证了"哈希可以作为指纹使用"。

② 单向性（Preimage Resistance）

已知输出，反推输入在计算上不可行。给你 2cf24dba...，你没法算出它是 "hello"。 唯一的办法是一个一个试——而 2256 这个空间大到宇宙毁灭也试不完。

2256 有多大？

可观测宇宙的原子总数大约是 2266 个。也就是说，SHA-256 的输出空间，和整个宇宙的原子数量是同一个量级。把地球上所有计算机连起来算到今天，暴力破解一个 SHA-256 哈希的概率仍然可以忽略不计。

③ 雪崩效应（Avalanche Effect）

输入改动哪怕 1 个比特，输出大约有一半的比特会翻转。上面 hello → hellp 的例子就是典型。 这条性质意味着：哈希值对输入极度敏感，你无法"微调"输入来得到一个想要的输出。

④ 抗碰撞（Collision Resistance）

找不到两个不同的输入，它们哈希值相同。注意这里的难度是"生日攻击"级别的： 找碰撞的复杂度约为 2128，仍然是天文数字。

2.3 比特币为什么需要哈希

哈希的四个性质，恰好对应比特币的四项需求：

性质在比特币里的用途
确定性所有人都能独立算出同一个区块哈希，用来标识区块、串成链
单向性矿工必须付出算力才能找到满足条件的哈希，这就是工作量证明的基础
雪崩效应改动历史记录会导致后续所有哈希变化，无法局部伪造
抗碰撞保证不可能伪造出一个"哈希相同但内容不同"的区块

2.4 亲手体验一次"挖矿"

挖矿听起来很玄，本质却简单到可以用十行代码说清楚： 不断改变一个数字，直到整串数据的哈希值满足某个条件。

我们让条件变得很容易——要求哈希以 0000 开头：

toy_mine.pypython
import hashlib

def sha256(b):
    return hashlib.sha256(b).hexdigest()

def mine(prefix="0000"):
    nonce = 0
    while True:
        data = f"block-data-{nonce}".encode()
        h = sha256(data)
        if h.startswith(prefix):
            return nonce, h
        nonce += 1

nonce, h = mine()
print("找到的 nonce:", nonce)
print("区块哈希:", h)
输出（每次运行不同）text
找到的 nonce: 15243
区块哈希: 0000cbcd3572bc8f2cca24eb70b8b779405d87e37d44d7d3cea2a02ba1a94bfd

这段代码里有一个关键角色：nonce。它本身没有任何含义，唯一的作用是 被反复修改，直到哈希碰巧满足条件。这就是挖矿的全部本质。

2.5 为什么"更难"意味着"更安全"

要求哈希以 0000 开头，意味着平均要试 164 = 65536 次。 每多一个 0，难度乘以 16。真实比特币网络要求的前导零不是 4 个，而是大约 19 个——相当于每次成功要试 1619 ≈ 7.6 × 1022 次。

关键在于：验证只需要一次哈希。任何人都能拿到那个区块，算一遍哈希，看看是不是真的以 19 个零开头。 生产要巨大成本，验证几乎免费——这个不对称性，是整个共识机制的支点。

为什么不能"作弊"

你可能想：既然只要哈希满足条件就行，那我随便编一个区块内容，只要它满足条件不就完了？

问题在于：区块内容里包含了前一个区块的哈希。你编造的区块必须接在真实的链上，也就是说，你必须从某个真实区块开始，把后面每一个区块重新挖一遍。而这些区块在真实网络中已经被成千上万台机器挖过了。你要在算力上赢过全网，才能让自己的链更长——这就是第 12 章要讲的"51% 攻击"门槛。

本章要点
  • 哈希函数把任意输入压成固定长度输出，具备确定性、单向性、雪崩效应、抗碰撞四性质。
  • SHA-256 的输出空间是 2256，暴力破解在物理上不可能。
  • 挖矿 = 改 nonce 直到哈希满足条件，生产成本极高，验证成本极低。
  • 这个"生产贵、验证便宜"的不对称性，是比特币安全的根基。

Chapter 03私钥、公钥与签名

哈希解决了"改不动"，签名解决了"谁有权改"。这一章我们亲手实现一套完整的椭圆曲线签名系统。

3.1 从一个直觉开始

现实中的签名有两个特点：只有你能签，但所有人都能认。你签合同，对方一看笔迹就知道是你。 电子世界需要同样的东西，但笔迹可以模仿，所以必须换一种机制。

非对称密码学给出了答案：一对数学上关联的密钥。

私钥 Private Key公钥 Public Key
作用生成签名验证签名
能否公开绝对不能可以随便公开
能否互相推导能算出公钥算不出私钥
本质一个 256 位的随机数椭圆曲线上的一个点

注意第三行的不对称：私钥 → 公钥很容易，公钥 → 私钥在计算上不可行。 这个单向性来自一个数学问题：离散对数问题。

3.2 椭圆曲线：比特币用的那一条

比特币使用的曲线叫 secp256k1，方程是 y² = x³ + 7，定义在一个特定的有限域上。 这条曲线上的所有点，加上一个"无穷远点"，构成一个数学结构，可以在上面定义"加法"。

加法有个重要性质：点 P 加上自己（记作 2P）很容易算，但反过来，"2P 是哪个 P 加出来的"却很难。 推广开来：已知 P，算 k·P（k 个 P 相加）很快；已知 k·P 和 P，反推 k 极其困难。这就是离散对数问题。

一句话理解

私钥 = k（一个大整数）
公钥 = k·G（G 是曲线上一个固定点，叫生成点）

正向乘一次就得到公钥，反向除一次——不存在这种运算。你只能暴力试 k，而 k 有 2256 种可能。

3.3 用 40 行代码实现 secp256k1

下面这段代码实现了椭圆曲线的点加与标量乘法，它完全使用 Python 标准库：

secp256k1.pypython
# secp256k1 曲线参数（这些是国际标准，全球通用）
P  = 2**256 - 2**32 - 977          # 有限域的模数
N  = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141
Gx = 0x79BE667EF9DCBBAC55A06295CE870B07029BFCDB2DCE28D959F2815B16F81798
Gy = 0x483ADA7726A3C4655DA4FBFC0E1108A8FD17B448A68554199C47D08FFB10D4B8

def inv(a, m):
    """模逆元：求 x 使 a*x ≡ 1 (mod m)"""
    return pow(a, -1, m)

def padd(p, q):
    """椭圆曲线上的点加法"""
    if p is None: return q
    if q is None: return p
    # 两点横坐标相同且纵坐标互为相反数 → 和为无穷远点
    if p[0] == q[0] and (p[1] + q[1]) % P == 0: return None
    if p == q:                                   # 切线斜率
        lam = (3*p[0]*p[0]) * inv(2*p[1], P) % P
    else:                                          # 割线斜率
        lam = (q[1]-p[1]) * inv(q[0]-p[0], P) % P
    x = (lam*lam - p[0] - q[0]) % P
    y = (lam*(p[0]-x) - p[1]) % P
    return (x, y)

def pmul(k, p=(Gx, Gy)):
    """标量乘法：算 k*p。用二进制展开（double-and-add），
       256 次循环就够，而不是 k 次加法。"""
    r = None
    while k:
        if k & 1: r = padd(r, p)
        p = padd(p, p)      # 倍点
        k >>= 1
    return r

先做一个自检：私钥为 1 时，公钥应该正好等于生成点 G。

verify.pypython

assert (x, y) == (Gx, Gy)   # 通过，说明实现是对的

# 现在用一个真实的私钥算公钥
priv = 1234567890

print(f"{x:064x}{y:064x}")

3.4 数字签名：ECDSA

有了密钥对，签名就水到渠成。ECDSA 的签名算法大致是这样：

签名流程

1. 把消息哈希成一个整数 z（这一步把任意长度消息压成 256 位）
2. 生成一个随机数 k，算出点 R = k·G，取 r = R 的 x 坐标
3. 计算 s = k−1(z + r·d) mod N，其中 d 是私钥
4. 签名就是 (r, s) 这一对数字

验证时，只需要公钥 Q = d·G：算出 u₁ = z·s−1，u₂ = r·s−1，然后检查点 (u₁·G + u₂·Q) 的 x 坐标是否等于 r。

ecdsa.pypython
import hashlib, secrets

def sign(z, d):
    """用私钥 d 对哈希值 z 签名"""
    while True:
        k = secrets.randbelow(N-1) + 1     # 必须用密码学安全随机数！
        r = pmul(k)[0] % N
        if r == 0: continue
        s = (inv(k, N) * (z + r*d)) % N
        if s == 0: continue
        return r, s

def verify(z, sig, Q):
    """用公钥 Q 验证签名"""
    r, s = sig
    w = inv(s, N)
    u1, u2 = (z*w) % N, (r*w) % N
    pt = padd(pmul(u1), pmul(u2, Q))
    return pt is not None and pt[0] % N == r

3.5 一个真实的历史事故：随机数不能复用

索尼 PS3 事件

2010 年，索尼 PS3 的固件签名被破解。原因不是曲线被攻破，而是签名时复用了同一个随机数 k。

从签名公式 s = k−1(z + r·d) 可以看到：如果两笔签名用了同一个 k，那么 r 也相同。此时有：
s₁ = k−1(z₁ + r·d)，s₂ = k−1(z₂ + r·d)
两式相减，k 和 d 都能直接解出来——私钥瞬间泄露。

所以代码里那句注释"必须用密码学安全随机数"不是客套话。用 random 模块或者复用 k，等于把私钥公开。

3.6 澄清一个流传很广的误解

很多人说"比特币用密码学加密了你的交易"。这句话是错的。

比特币交易是明文的。转账金额、发送方公钥、接收方地址，全部清清楚楚写在区块链上，谁都能看。 比特币用到的是数字签名，不是加密。签名保证的是"完整性"和"授权"，而不是"保密性"。

这两者的区别很大：

加密 Encryption签名 Signature
目的让别人看不懂让别人改不了、赖不掉
用谁的密钥接收方公钥加密，接收方私钥解密发送方私钥签名，发送方公钥验证
比特币用了吗基本没用（只有钱包文件会加密）核心机制
本章要点
  • 私钥是 256 位随机数，公钥 = 私钥 × G，单向不可逆（离散对数问题）。
  • secp256k1 的完整实现只需 40 行 Python，核心是点加和二进制标量乘法。
  • ECDSA 签名 (r, s) 保证内容改了签名就失效，这就是防篡改。
  • 签名随机数 k 绝不能复用或使用弱随机源，PS3 就是栽在这上面。
  • 比特币用签名而非加密，交易内容是公开的。

Chapter 04哈希链与 Merkle 树

有了哈希和签名，还差一个结构：如何把成千上万笔交易组织成一串"牵一发而动全身"的记录。答案是把哈希串起来。

4.1 哈希链：把过去锁死

假设我们把交易打包成一个个区块。每个区块里放一个字段：前一个区块的哈希。 于是一个区块的内容决定了它自己的哈希，而这个哈希又被写进下一个区块。这就是哈希链。

4.2 区块头：80 字节决定一切

比特币区块分成两部分：区块头（80 字节）和交易列表（大小不定）。区块头只有 6 个字段：

字段长度含义
version4 字节协议版本号，也用于软分叉信号（BIP9）
prev_block_hash32 字节前一个区块头的双重 SHA-256，小端存储
merkle_root32 字节本区块所有交易构成的 Merkle 树根
timestamp4 字节矿工写入的 Unix 时间戳
bits4 字节当前难度目标的压缩编码
nonce4 字节矿工反复尝试的那个数字

整整 80 字节。区块哈希就是对这 80 字节做两次 SHA-256。注意这个细节： 交易数据不直接参与区块哈希，而是通过 merkle_root 间接参与。这个设计让轻节点可以在不下全部交易的情况下验证交易是否存在。

为什么是"双重" SHA-256？

比特币几乎所有哈希都算两遍：SHA256(SHA256(data))。中本聪没有正式解释原因，流传最广的推测是防"长度扩展攻击"（length extension attack）——SHA-256 的 Merkle-Damgård 结构允许在已知哈希的情况下追加数据并算出新哈希，双重哈希能有效阻断这种攻击。

4.3 Merkle 树：一万笔交易的指纹

一个区块可能有几千笔交易。如果 merkle_root 是"把所有交易拼起来再哈希"，那么想验证其中一笔交易， 就必须下载全部交易。Merkle 树解决了这个问题。

4.4 Merkle 证明：轻钱包的秘密

假设你想证明 Tx1 确实在这个区块里，但你不想下载 Tx2、Tx3、Tx4。Merkle 树允许你只提供：

  • H2（和 Tx1 配对的那个哈希）
  • H34（上一层的兄弟节点）
  • Root（区块头里的，你本来就信）

然后自己算：H1 = H(Tx1) → H12 = H(H1‖H2) → Root' = H(H12‖H34)，看 Root' 是否等于 Root。

区块有 n 笔交易时，证明只需要 log₂(n) 个哈希。 4000 笔交易只需要 12 个哈希（约 384 字节），而不是下载整个区块（1MB 以上）。 手机上的轻钱包（SPV 钱包）就是靠这个工作的。

merkle.pypython
import hashlib

def dsha(b):
    """比特币的双重 SHA-256"""
    return hashlib.sha256(hashlib.sha256(b).digest()).digest()

def merkle_root(txids):
    """txids 是各交易 txid 的字节串列表（内部字节序）"""
    layer = list(txids)
    if not layer:
        return b"\x00" * 32
    while len(layer) > 1:
        # 奇数个节点时，复制最后一个与自己配对
        if len(layer) % 2:
            layer.append(layer[-1])
        layer = [dsha(layer[i] + layer[i+1])
                 for i in range(0, len(layer), 2)]
    return layer[0]

# 用 4 笔交易试一下
txs = [dsha(f"tx{i}".encode()) for i in range(1, 5)]
root = merkle_root(txs)
print("merkle root:", root[::-1].hex())
一个真实的漏洞

上面代码里"奇数个节点时复制最后一个"这个做法，历史上造成了一个叫 CVE-2012-2459 的漏洞。攻击者可以构造一个包含重复交易的区块，使它的 merkle_root 与正常区块相同，从而制造出两个不同但"合法"的区块，导致网络分叉。这个漏洞在 2012 年被修复，但它说明了一个道理：再小的设计细节，在分布式系统里都可能被放大成安全问题。

本章要点
  • 哈希链把每个区块的哈希写进下一个区块，改动历史需要重做后续全部工作量。
  • 区块头只有 80 字节，6 个字段；区块哈希 = 双重 SHA-256(区块头)。
  • Merkle 树把 n 笔交易压成 32 字节根哈希，验证单笔交易只需 log₂(n) 个哈希。
  • 轻钱包（SPV）靠 Merkle 证明工作，不下全量交易也能验证。
PART TWO

账本

数据结构只是骨架，账本里到底存了什么才是关键。这一部分我们打开一个真实的区块，把每一笔交易拆到字节级别看清楚：钱从哪来，到哪去，凭什么说这笔钱是你的。

Chapter 05UTXO：比特币没有账户

这是比特币最反直觉的设计。你的钱包里没有"余额"这个字段，账本上也没有"账户"这张表。

5.1 先看银行怎么记

传统银行用的是账户模型（Account Model）：

账户余额
Alice1.00000000 BTC
Bob0.00000000 BTC

Alice 转 0.3 给 Bob，就是改两个数字：Alice 减 0.3，Bob 加 0.3。简单直接。

5.2 比特币怎么记：UTXO

比特币用的是未花费交易输出模型（UTXO, Unspent Transaction Output）。 可以类比成现金：你的钱包里没有"余额"这个概念，只有一张张具体的钞票。 你有 100 块，可能是"一张 50 + 两张 20 + 一张 10"，而不是一个数字 100。

在比特币里，这些"钞票"就是 UTXO：

5.3 找零：为什么转账会有两个输出

Alice 只有一张 1 BTC 的"钞票"，要付 Bob 0.3 BTC。现金世界怎么做？给 Bob 0.3，自己拿回 0.7。 比特币完全一样：把 1 BTC 整张花掉，输出 0.3 给 Bob，输出 0.6999 给自己，剩下的 0.0001 就是手续费。

手续费的本质

手续费不是一个"字段"。它只是输入总额减去输出总额的差额。这笔差额没有对应的输出，所以它实际上被矿工收走了（矿工在 coinbase 交易里把这笔钱记给自己）。

所以你在钱包里看到的"手续费 0.0001 BTC"，背后是：输入 1.00000000 − 输出 0.30000000 − 输出 0.69990000 = 0.00010000。

5.4 UTXO 模型的三个后果

后果说明
并行验证每笔交易可以独立验证（只要检查引用的 UTXO 存在且未花费），不需要按顺序执行。这让比特币天然支持并行处理。
隐私问题找零输出通常回到自己的新地址，但如果你把找零发回原地址，就暴露了"这两个地址属于同一个人"。这是第 14 章要讲的地址复用问题。
UTXO 膨胀每笔交易都会创建新 UTXO，同时消耗旧的。小额 UTXO 太多会导致转账时手续费很高（因为输入越多，交易字节数越大）。这叫"粉尘"问题。

6.1 交易的结构

一笔交易的序列化格式如下，全部使用小端序（little-endian）：

prev_vout4 字节被花费的是那笔交易的第几个输出
script_sig变长解锁脚本（提供签名和公钥）

每个输出只有两个字段：

字段长度说明
value8 字节金额，单位聪（整数！）

这是一个非常关键的设计。交易的输入只写"我在花哪张 UTXO"，不写"这张 UTXO 有多少钱"。金额需要从账本里查。

为什么？因为如果输入自己声明金额，攻击者可以谎报"我这张 UTXO 有 100 万 BTC"。必须由验证者自己去 UTXO 集合里查真实金额。手续费也就是在这个查证过程中算出来的。

parse_tx.pypython
import hashlib

class Reader:
    """一个最简单的字节流读取器"""
    def __init__(self, data):
        self.d = data
        self.i = 0
    def take(self, n):
        b = self.d[self.i:self.i+n]
        self.i += n
        return b
    def u32(self):
        return int.from_bytes(self.take(4), "little")
    def u64(self):
        return int.from_bytes(self.take(8), "little")
    def varint(self):
        """比特币的变长整数：按首字节决定长度"""
        n = self.take(1)[0]
        if n < 0xfd: return n
        if n == 0xfd: return int.from_bytes(self.take(2), "little")
        if n == 0xfe: return self.u32()
        return self.u64()

def parse_tx(raw):
    r = Reader(raw)
    tx = {"version": r.u32(), "vin": [], "vout": []}

    for _ in range(r.varint()):
        prev = r.take(32)
        tx["vin"].append({
            "prev_txid": prev[::-1].hex(),   # 转回大端给人看
            "prev_vout": r.u32(),
            "script_sig": r.take(r.varint()).hex(),
            "sequence": r.u32(),
        })

    for _ in range(r.varint()):
        tx["vout"].append({
            "value_sat": r.u64(),
            "script_pubkey": r.take(r.varint()).hex(),
        })

    tx["locktime"] = r.u32()
    tx["size"] = len(raw)
    return tx

def txid(raw):
    """txid = 双重 SHA-256 后反转字节序"""
    return hashlib.sha256(hashlib.sha256(raw).digest()).digest()[::-1].hex()

6.4 txid 为什么和原始字节不一样

txid 是交易原始字节的双重 SHA-256，但有两个容易踩坑的细节：

  • 算两遍：SHA256(SHA256(raw))，不是一遍。
  • 字节序反转：协议内部用小端存储，但展示给人看时用大端。所以你在区块浏览器上看到的 txid，是把 32 字节反过来的结果。
新手最常犯的错

自己写代码算 txid，算出来和浏览器对不上——90% 是因为忘了反转字节序。记住：协议里的一切都是小端，展示给人类的一切都是大端。

本章要点
  • 交易 = version + 输入列表 + 输出列表 + locktime，全部小端序。
  • 输入只写"花哪张 UTXO"，不写金额，金额要从账本查——这是防伪造的关键。
  • 输出 = 金额（8 字节整数）+ 锁定脚本。
  • txid = 双重 SHA-256 后反转字节序。

Chapter 07脚本：可编程的锁

"这笔钱谁能花"这件事，比特币不是用字段写死的，而是用一段小程序表达。这就是脚本系统。

7.1 两种脚本，一前一后

每笔交易涉及两个脚本：

锁定脚本 scriptPubKey解锁脚本 scriptSig
在哪旧交易的输出里新交易的输入里
作用定义"谁能花这笔钱"提供"我是那个人的证明"
类比一把锁开锁的钥匙
何时写收款时，由付款方写花费时，由收款方写

验证时，把两个脚本拼起来执行：scriptSig 先执行，结果留在栈上，然后执行 scriptPubKey。如果最后栈顶为真，就通过。

7.2 脚本是一门语言

比特币脚本是一门基于栈的、非图灵完备的语言。它没有循环、没有跳转，只有一堆操作码（opcode）顺序执行。

为什么要故意限制它？因为图灵完备的语言会导致停机问题——你无法事先知道一段代码要跑多久，也就无法防止有人写一个死循环把全网节点卡死。非图灵完备 = 可预测的执行成本。

栈是什么

想象一摞盘子。你只能往顶上放（push），也只能从顶上拿（pop）。这叫"后进先出"（LIFO）。脚本的每一步都在这摞盘子上操作。

7.6 脚本的发展方向：从"暴露条件"到"隐藏条件"

早期脚本（P2PKH、P2SH）有个隐私问题：花费时要把完整脚本亮出来。比如一个 2-of-3 多签，全网都知道这是个多签，也都看到是哪 3 个公钥。

Taproot（第 16 章）改变了这一点：你可以只暴露实际用到的那一条分支，其他分支永远隐藏。这让复杂合约在链上看起来和普通转账一模一样。

本章要点
  • 锁定脚本定义"谁能花"，解锁脚本提供"我是那个人的证明"，两者拼接执行。
  • 脚本是基于栈的、非图灵完备的语言——故意不支持循环，避免停机问题。
  • P2PKH 的执行顺序：DUP → HASH160 → 比对 → CHECKSIG。
  • 地址前缀对应脚本类型：1=P2PKH，3=P2SH，bc1q=SegWit v0，bc1p=Taproot。
  • 脚本演进的趋势是隐藏条件：从全网可见，到只暴露用到的分支。

import hashlib

def hash160(b):
    """比特币公钥哈希：先 SHA256 再 RIPEMD160，得到 20 字节"""
    return hashlib.new("ripemd160", hashlib.sha256(b).digest()).digest()

def base58(b):
    """Base58 编码：去掉了 0 O I l 这些容易看错的字符"""
    A = "123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz"
    n = int.from_bytes(b, "big")
    s = ""
    while n:
        n, r = divmod(n, 58)
        s = A[r] + s
    # 处理前导零字节，每个零字节对应一个 '1'
    return "1" * (len(b) - len(b.lstrip(b"\x00"))) + s

def b58check(payload):
    """Base58Check：附加 4 字节校验和，防止输错地址"""
    chk = hashlib.sha256(hashlib.sha256(payload).digest()).digest()[:4]
    return base58(payload + chk)

8.3 为什么公钥要压缩

未压缩公钥是 65 字节（0x04 + x + y），压缩公钥是 33 字节（0x02/0x03 + x）。

秘密在于：给定 x 和曲线方程 y² = x³ + 7，y 只有两个可能值（一正一负，即 y 和 P−y）。 所以只需要 1 个比特记录 y 的奇偶性，就能完整还原这个点。65 字节 → 33 字节，节省近一半。

一个历史遗留问题

同一个私钥，用未压缩公钥和压缩公钥，会算出两个完全不同的地址。早期钱包用未压缩，后来改为压缩。所以如果你在 2012 年前用过某个私钥，恢复时可能需要在两种地址类型之间切换才能找到你的币。这不是 bug，是历史包袱。

8.4 Bech32：新一代地址编码

SegWit（第 17 章）引入了新地址格式，以 bc1 开头。它用的是 Bech32 编码，特点是：

  • 全小写（或全大写），没有大小写混淆问题
  • 更强的纠错能力：能检测出最多 4 个字符的错误，且能定位错误位置
  • 更短：SegWit 交易的手续费按"重量"算，Bech32 地址对应的脚本更省空间
bech32.pypython
CHARSET = "qpzry9x8gf2tvdw0s3jn54khce6mua7l"

def polymod(v):
    GEN = [0x3b6a57b2, 0x26508e6d, 0x1ea119fa, 0x3d4233dd, 0x2a1462b3]
    chk = 1
    for x in v:
        b = chk >> 25
        chk = ((chk & 0x1ffffff) << 5) ^ x
        for i in range(5):
            chk ^= GEN[i] if ((b >> i) & 1) else 0
    return chk

def hrp_expand(h):
    return [ord(c) >> 5 for c in h] + [0] + [ord(c) & 31 for c in h]

def convertbits(data, f, t, pad=True):
    """8 位分组 → 5 位分组，因为 Bech32 的字母表只有 32 个字符"""
    acc = bits = 0; ret = []
    for v in data:
        acc = (acc << f) | v; bits += f
        while bits >= t:
            bits -= t
            ret.append((acc >> bits) & ((1 << t) - 1))
    if pad and bits:
        ret.append((acc << (t - bits)) & ((1 << t) - 1))
    return ret

def bech32_encode(hrp, data):
    values = hrp_expand(hrp) + data
    pm = polymod(values + [0]*6) ^ 1
    checksum = [(pm >> 5*(5-i)) & 31 for i in range(6)]
    return hrp + "1" + "".join(CHARSET[d] for d in data + checksum)

# SegWit v0 地址：witness version 0 + 公钥哈希

Chapter 09P2P 网络：消息怎么传

比特币没有服务器。每个节点都是平等的，每个节点都在说、都在听。这一章我们看看它们在说什么。

9.1 三类节点

类型保存什么验证什么典型设备
全节点 完整区块链 + UTXO 集合 从创世块开始验证全部规则 PC / 树莓派，需 600GB+ 磁盘
轻节点（SPV） 只存区块头（80 字节 × 高度） 只验证工作量证明和 Merkle 证明 手机钱包
矿工 通常是全节点 + 挖矿设备 全节点验证 + 构造候选区块 ASIC 矿机

全节点是比特币的"宪法法院"。它们不投票、不选举，只是各自独立地验证每一笔交易、每一个区块是否符合规则。 一个不遵守规则的矿工挖出的块，全节点会直接丢弃——矿工可以决定打包什么，但不能决定规则是什么。

轻节点的安全等级不同

SPV 轻节点只验证"这个区块有足够的工作量"和"这笔交易在这个区块里"，但它不验证区块里的其他规则（比如有没有超发）。理论上，一个算力占多数的矿工可以给轻节点喂一个违反规则的区块，轻节点会接受。

所以真正的安全来自运行全节点。这也是为什么"自己跑一个节点"在比特币社区被视为一种责任，而不是极客爱好。

节点之间用一套自定义的二进制协议通信（默认端口 8333）。每条消息的格式是：

9.3 一个新节点的加入过程

新节点启动时，怎么知道该连谁？靠 DNS 种子（DNS seeds）——一组由社区维护的域名， 查询后会返回一批长期在线节点的 IP。连上之后，通过 addr 消息不断发现新节点， 最终形成一个去中心化的连接图。

9.4 Gossip：消息如何传遍全网

比特币不用广播（没有"向所有人发一条消息"的机制）。它用的是 gossip 协议： 节点收到一条新交易，验证通过后，转发给一部分邻居（默认 8 个出站连接）。

这个传播过程有三个特点：

  • 指数扩散：每一跳节点数翻倍，几秒钟就能覆盖全球大部分节点。
  • 先去重：节点记住最近见过的消息哈希，不重复转发，否则会形成广播风暴。
  • 先验证再转发：无效交易会被直接丢弃，不会污染网络。这就是为什么垃圾交易很难传播。
为什么是 inv + getdata，而不是直接发 tx？

如果每个节点收到新交易就立刻把完整内容推给所有邻居，带宽会爆炸（同一笔交易你可能收到 8 次）。

比特币的做法是：先发一个只有 32 字节哈希的 inv。邻居一看"这个哈希我还没见过"，才回 getdata 要完整内容。这样同一笔交易在你这里只会被下载一次。

9.5 网络分区的后果

网络分区（比如海底光缆断了）会导致不同地区的节点看到不同的链。这不是灾难，因为第 12 章要讲的 "重组"机制会在网络恢复后自动统一到工作量最大的那条链上。

真正危险的是故意制造的分区——比如通过 BGP 劫持把某个矿池的流量全部截断。 2015 年确实发生过针对比特币网络的大规模 BGP 劫持事件，但网络的自我修复能力让它只造成了短暂的临时分叉。

本章要点
  • 全节点验证全部规则，轻节点只验证工作量证明——安全等级不同。
  • 矿工能决定打包什么，但不能决定规则是什么，规则由全节点执行。
  • 协议用 inv（只发哈希）+ getdata（按需拉取）避免带宽浪费。
  • 新节点靠 DNS 种子 + addr 消息发现邻居，靠 gossip 传播消息。

Chapter 10挖矿与工作量证明

10.1 "目标值"：一个可以调高调低的门槛

第 2 章我们用"哈希以 0000 开头"作为条件。但比特币不能用"前导零个数"这种离散的条件——它需要连续可调的难度。 所以比特币用的是一个数值门槛（target）：区块哈希必须小于 target。

哈希值以十六进制表示，所以"小于某个 target"在视觉上就表现为"前面有很多个 0"。 这个 target 被压缩成 4 字节存在区块头的 bits 字段里。

bits.pypython
def bits_to_target(bits):
    """把 4 字节压缩难度还原成 256 位目标值
       格式：首字节是指数，后 3 字节是尾数
       target = 尾数 × 256^(指数 - 3)"""
    exp  = bits >> 24
    mant = bits & 0x007fffff
    if exp <= 3:
        return mant >> (8 * (3 - exp))
    return mant << (8 * (exp - 3))

def target_to_difficulty(t):
    """难度 = 基准 target / 当前 target"""
    D1 = 0x00000000FFFF0000000000000000000000000000000000000000000000000000
    return D1 / t

10.5 矿池：把彩票变成工资

单人挖矿是买彩票：按上面算的，一台普通矿机可能要跑几年才中一次。矿工想要的是稳定收入，于是有了矿池。

矿池的逻辑：

  1. 矿池把候选区块头分发给所有参与的矿机。
  2. 每台矿机在各自的 nonce 空间里搜索。
  3. 找到"低于矿池设定的较低门槛"的解（叫 share），立刻上报，证明自己确实在干活。
  4. 矿池按 share 数量分配奖励。如果运气好，某个 share 恰好低于网络 target，那就是一个真正的区块。
矿池的中心化隐忧

矿池让算力集中到了少数几个运营者手里。如果某几个大矿池联合起来，理论上能控制超过 51% 的算力。这是比特币社区长期关注的问题。

缓解措施包括：矿池不直接控制矿机的私钥（矿工可以随时切换池子）、以及像 Stratum V2 这样让矿工自己选择打包哪些交易的协议升级。

本章要点
  • 挖矿条件不是"前导零个数"，而是区块哈希 < target；target 压缩存在 bits 字段。
  • 难度 = 基准 target / 当前 target，目前是 86 万亿倍级别。
  • nonce 只有 4 字节，用完就改 coinbase 里的 extraNonce 来改变 Merkle 根。
  • coinbase 交易金额有硬上限：区块补贴 + 手续费，超发会被全节点拒绝。
  • 矿池把"彩票"变成"工资"，但也带来了算力集中化的隐忧。

Chapter 11难度调整与 2100 万

比特币最精妙的设计之一：一套完全自动运行、不需要任何人干预的货币政策。

11.1 每 2016 个块调整一次难度

2016 个块 × 10 分钟 = 两周。每挖出 2016 个块，全网节点会重新计算一次难度，公式是：

难度调整公式plain
新难度 = 旧难度 × (实际用时 / 20160 分钟)

其中 20160 = 2016 块 × 10 分钟

规则：
  · 结果被限制在 1/4 到 4 倍之间（防止极端波动）
  · 算力上升 → 出块变快 → 实际用时 < 20160 → 难度上调
  · 算力下降 → 出块变慢 → 实际用时 > 20160 → 难度下调

这是一个负反馈回路。无论全球算力怎么涨跌，出块时间都会被拉回 10 分钟附近。 换句话说：比特币用难度这个变量，把"算力"这个不可控因素，转换成了"安全性"这个可控指标。

算力暴涨时，难度跟着涨，攻击成本跟着涨；算力暴跌时，难度下降，网络仍然能维持运转。 这个自适应机制让比特币从一台笔记本电脑能挖矿，一路撑到了今天的 ASIC 矿场。

比"2100 万"更重要的东西

很多人把比特币的价值归于"总量有限"。但更本质的是：这个上限是代码里写死的，没有任何人可以修改。

要改总量，需要修改共识规则，而这需要几乎全网节点同时接受——这在实践中不可能发生。不是"有法律禁止增发"，而是技术上做不到。这种"制度硬约束"才是稀缺性的来源。

11.3 手续费市场：2140 年之后靠什么

区块补贴会一直减半下去，大约在 2140 年归零。到那时，矿工收入将完全来自手续费。

手续费市场是这样运作的：

  • 区块空间有限（权重上限 4,000,000 WU，约等于 1–4 MB 数据），供给是固定的。
  • 想尽快确认的人愿意付更高的费率（sat/vB）。
  • 矿工按费率从高到低挑交易打包，价高者先上车。
  • 费率由市场供需实时决定，没有固定价格。
一个长期争论

手续费能否支撑网络安全？这是一个悬而未决的问题。如果将来链上交易量不足，手续费收入可能远低于现在的区块补贴，矿工可能退出，算力下降，安全性降低。

乐观派的理由是：随着区块补贴减少，比特币的市值和交易需求会同步增长，手续费会自然补上。悲观派认为这需要每笔交易付极高的费用，会排除小额支付场景。

闪电网络（第 18 章）被认为是这个问题的部分答案：把海量小额交易移到链下，链上只保留结算交易，让有限的区块空间承载更高价值的结算。

本章要点
  • 每 2016 块（约两周）调整一次难度，公式是"实际用时 / 20160 分钟"。
  • 难度调整把不可控的算力波动，转化为可控的安全性指标。
  • 区块补贴每 210,000 块减半，收敛到约 2100 万 BTC。
  • 上限不可修改不是因为法律，而是因为技术上需要全网共识。
  • 区块补贴约在 2140 年归零，之后矿工收入全靠手续费。

Chapter 12分叉、重组与 51%

如果两个矿工同时挖出区块怎么办？如果有人试图改写历史怎么办？这一章讲比特币如何处理冲突。

12.1 临时分叉是常态，不是故障

假设矿工 A 和矿工 B 几乎同时找到了一个合法区块。由于网络传播有延迟，一半节点先看到 A 的块， 另一半先看到 B 的块。此时网络暂时分裂成两条链：

"最长链"其实是"最重链"

常说的"最长链原则"是个不准确的简称。准确规则是：选择累计工作量最大的那条链。

为什么有区别？因为在难度不同的历史时期，"块数多"不等于"工作量大"。一个从低难度时期延续下来的长链，可能总工作量小于一条短但难度高的链。比特币的规则是比总工作量，不是比块数。

12.2 为什么重组不会无限扩大

一个交易被打包进区块后，每多一个块压在上面，被推翻的难度就指数级上升。因为要推翻它， 攻击者必须从那个块开始，重新挖出所有后续的块，并且要比诚实网络挖得更快。

确认数被重组概率（假设攻击者算力 30%）典型场景
0（仅广播）高小额、即时消费
1低小额支付
3极低一般交易
6可忽略交易所充值、大额结算（行业惯例）
100几乎不可能coinbase 奖励可花费的门槛

"6 个确认"不是协议规定的，而是行业惯例。它的数学依据是：在诚实算力占多数的情况下， 攻击者连续追平 6 个块的概率随确认数指数衰减。

12.3 软分叉 vs 硬分叉

当需要修改规则时，有两种方式：

软分叉 Soft Fork硬分叉 Hard Fork
规则变化收紧：新规则是旧规则的子集放宽：新规则不接受旧规则允许的东西
旧节点仍然接受新块（只是不理解新功能）会拒绝新块，被分裂出去
是否分裂链不分裂（只要多数算力支持）分裂成两条链，各走各的
需要多少支持多数算力即可几乎全网一致
例子P2SH（2012）、SegWit（2017）、Taproot（2021）Bitcoin Cash（2017）、Bitcoin SV（2018）
为什么软分叉更受欢迎

软分叉是"向后兼容"的：没升级的节点仍然能参与网络，只是无法使用新功能。这样避免了链分裂，也不需要说服所有人同时升级。

代价是软分叉的实现往往更复杂、更别扭。SegWit 就是典型——为了做成软分叉，它不得不把见证数据塞进一个旧节点会忽略的位置，导致代码里有大量"看起来很奇怪"的设计。

12.4 51% 攻击：能做什么，不能做什么

如果某个攻击者掌握了超过一半的算力，他能做什么？

能做不能做
· 阻止某些交易被打包（审查）
· 逆转自己刚发出的交易（双花）
· 制造链重组，让最近几个块失效
· 空块挖矿，让网络变慢 		· 偷别人的币（没有私钥就签不出交易）
· 凭空增发（全节点会拒绝超发的块）
· 花掉别人的 UTXO
· 修改很久以前的区块（成本指数级上升）

注意最关键的一条：51% 算力无法偷币。算力只影响"谁能打包、打包什么顺序"， 它不能伪造签名。这是密码学层和共识层分离带来的安全冗余。

51% 攻击的真实案例

比特币主网从未被 51% 攻击成功过。但一些算力较小的币种被攻击过多次，例如 Ethereum Classic（2019、2020 年各一次）和 Bitcoin Gold（2018、2020 年）。攻击手法通常是与交易所配合的双花：先充值，等交易所确认后卖出，然后广播一条更长的链让充值交易失效。

这说明了什么？安全性正比于算力规模。算力小的链，攻击成本低，就容易被盯上。比特币的算力规模本身就是它的护城河。

本章要点
  • 临时分叉是常态，靠"累计工作量最大"规则自动收敛。
  • 准确说法是"最重链"而非"最长链"——比的是总工作量，不是块数。
  • 软分叉收紧规则、向后兼容；硬分叉放宽规则、导致链分裂。
  • 51% 算力能双花和审查，但不能偷币、不能增发。
  • 确认数越多，重组成本指数级上升；6 确认是行业惯例而非协议规定。

13.2 Mempool：交易的候车室

Mempool（内存池）是每个节点本地保存的"待确认交易集合"。它不是全网统一的——每个节点的 mempool 内容都不一样， 取决于它收到了哪些交易、以及它自己的容量策略。

13.3 费率：为什么同一时间价格差 100 倍

交易大小不是按金额算的，而是按字节数算的。同样一笔转账，输入越多，字节数越大，费用越高：

交易类型典型大小1 sat/vB 时的手续费
1 输入 2 输出 P2PKH约 226 vB226 聪
1 输入 2 输出 P2WPKH（SegWit）约 141 vB141 聪
10 输入 2 输出 P2PKH约 1,480 vB1,480 聪
1 输入 2 输出 P2TR（Taproot）约 111 vB111 聪

注意 SegWit 和 Taproot 的优势。这就是为什么现在钱包默认使用 bc1q / bc1p 地址—— 同样的转账，字节数少 40%，费用也就少 40%。

vB（虚拟字节）是什么

SegWit 引入了一个"权重（weight）"概念来计价：

weight = 基础数据 × 4 + 见证数据 × 1
vsize (vB) = weight / 4

见证数据（签名部分）打 1 折，所以把签名挪到见证区就能降低费用。这个设计既降低了费用，又避免了直接扩容区块带来的硬分叉问题。

13.4 卡住了怎么办：RBF 和 CPFP

如果费率估低了，交易可能几小时甚至几天不确认。有两种补救方式：

RBF（Replace-By-Fee，费用替换）

用一笔手续费更高的新交易，替换掉原来的那笔。前提是原交易的 sequence 字段 标记了"允许替换"（通常设为 0xFFFFFFFD 或更低）。

注意：RBF 曾经引起争议，因为它让"0 确认交易"变得不可靠——收款方以为收到钱了， 结果付款方用更高费用把交易替换掉。现在 RBF 已被普遍接受，但商家不应该接受 0 确认的大额支付。

CPFP（Child-Pays-For-Parent，子为父付费）

适用于你是收款方的场景。既然那笔卡住的交易是别人发的，你没法改它， 但你可以花掉它的输出，发一笔手续费极高的新交易。矿工为了拿到新交易的高费用， 必须把它的父交易也一起打包。

RBFCPFP
谁用付款方收款方（或付款方自己）
前提原交易标记了可替换无前提
代价重新签一笔交易要为父子两笔交易一起付高费率

13.5 用代码算一下手续费

fee.pypython
def fee_rate(inputs_sat, outputs_sat, vsize_vb):
    """费率 = 手续费 / 虚拟字节数，单位 sat/vB"""
    fee = sum(inputs_sat) - sum(outputs_sat)
    return fee, fee / vsize_vb

# 第 6 章那笔交易：输入 1 BTC，输出 0.3 + 0.6999

    vsize_vb    = 225,

print(f"费率: {rate:.2f} sat/vB")      # 44.44 sat/vB

need = target_rate * 225

14.3 地址复用：一个被严重低估的隐私问题

很多人把钱包地址当成银行账号用——发给所有人，一直用同一个。这在比特币里是灾难性的做法。

原因在于：区块链是完全公开的。一旦某个地址被关联到你的身份（比如交易所 KYC、公开募捐、社交媒体），

  • 这个地址的全部历史都被曝光：每一笔收入、每一笔支出、余额、时间。
  • 通过交易的输入合并关系，可以推断出哪些地址属于同一个人——因为一笔交易的多个输入通常由同一个钱包签名。
  • 连带暴露与你有资金往来的所有人。你给朋友转账，朋友的地址也就被暴露了。
一个真实的教训

有一个著名的案例：某位早期参与者因为在论坛上公开过一个收款地址，被链上分析公司顺藤摸瓜， 推断出了他的整个地址簇，包括他从未公开过的持仓。这些信息后来被用于针对他的攻击。

结论：每次收款都用新地址。这不是偏执，这是基本功。第 15 章的 HD 钱包就是为此而生的。

14.4 助记词的三条铁律

铁律为什么
永不数字化 不拍照、不打字存进云笔记、不发微信、不存密码管理器（除非是专用的、离线的）。任何联网设备上的截图都可能被同步、被备份、被入侵。
永不分片保存 把 12 个词分成三份存三个地方，看起来更安全，实际上降低了安全性——任何一个地方泄露都会减少攻击者需要猜的位数。正确做法是完整备份多份，或使用 Shamir 秘密分享（BIP39 的 passphrase 也可以起到类似作用）。
永不输入到任何网站 没有任何正规服务会要求你输入助记词。任何索要助记词的页面，100% 是钓鱼。硬件钱包的助记词只需要在设备本体上输入（或通过设备键盘）。
关于"脑钱包"

有人提议用一个自己记得住的句子（比如一句诗）直接哈希成私钥，这样就不需要备份了。这是极其危险的。

人类的"随机"选择空间远小于 2256。攻击者可以把常见书籍、歌词、名言全部哈希一遍，做成字典进行暴力破解。事实上，早期的"脑钱包"地址几乎全部被搬空了。

随机性必须来自密码学安全的随机源。你的大脑不是。

本章要点
  • 钱包里没有币，只有私钥；地址和历史都可以重新生成。
  • 热钱包方便但暴露于网络攻击，冷钱包安全但操作繁琐，应该分层使用。
  • 硬件钱包的核心是私钥永不离开芯片，只进出待签内容和签名。
  • 地址复用会暴露你的全部历史、地址簇关系和交易对手，每次收款都用新地址。
  • 助记词：不数字化、不分片、不输入到任何网站。

12 个英文单词，如何变出无限多个地址，而且随时可以恢复？这一章讲 BIP32 / BIP39 / BIP44 这套标准。

15.1 问题：如何备份无限多个私钥

如果每个地址都需要单独备份私钥，那"每次收款用新地址"这个建议就没法落地——你会有一万个私钥要管。 HD 钱包（Hierarchical Deterministic Wallet，分层确定性钱包）解决了这个问题：

一句话概括

你只需要备份一个种子，所有私钥都能从这个种子确定性地推导出来。

"确定性"意味着：同一个种子，在任何钱包软件、任何时间、任何设备上，推导出的第 1000 个地址永远是一样的。

15.2 三层结构：熵 → 助记词 → 种子 → 私钥

15.3 BIP39：熵与助记词的互转

助记词不是"随便挑 12 个词"。它是把 128 位随机熵 + 4 位校验和，按 11 位一组切成 12 段， 每一段映射到一张 2048 词的固定词表。

128 位熵 = 11 位 × 12 段plain
熵（128 位）+ 校验和（4 位）= 132 位 = 12 × 11 位
每个 11 位数字（0–2047）→ 词表里的一个单词

128 位熵 → 12 个词
160 位熵 → 15 个词
192 位熵 → 18 个词
224 位熵 → 21 个词
256 位熵 → 24 个词
bip39.pypython
import hashlib, unicodedata

def entropy_to_mnemonic(entropy, words):
    """words 是 BIP39 的 2048 词表（这里省略）"""
    cs_len = len(entropy) * 8 // 32          # 128 位熵 → 4 位校验
    h = hashlib.sha256(entropy).digest()
    bits = bin(int.from_bytes(entropy, 'big'))[2:].zfill(len(entropy)*8)
    cs   = bin(h[0])[2:].zfill(8)[:cs_len]
    total = bits + cs                          # 132 位
    return [words[int(total[i:i+11], 2)] for i in range(0, len(total), 11)]

def mnemonic_to_seed(mnemonic, passphrase=""):
    """助记词 → 64 字节种子，注意 NFKD 规范化"""
    m = unicodedata.normalize("NFKD", mnemonic)
    s = unicodedata.normalize("NFKD", "mnemonic" + passphrase)
    return hashlib.pbkdf2_hmac("sha512", m.encode(), s.encode(), 2048, 64)

15.5 xpub：只读的"监看密钥"

BIP32 有个很实用的性质：普通派生（非硬化）可以在不知道私钥的情况下进行。 你只需要一个 xpub（扩展公钥），就能推导出所有的公钥和地址，但无法签任何交易。

xpub 也需要保护

xpub 虽然不能花钱，但泄露它等于泄露你所有的地址——包括还没用过的。攻击者可以提前知道你的完整地址列表， 监控你的余额变化，甚至在你收款前就准备好针对性的钓鱼。

所以 xpub 只应该交给可信的、只读的系统（比如自己的记账工具），不要随便贴到网上。

Chapter 16多签、时间锁与 Taproot

单个私钥是单点故障。这一章讲如何用脚本构建更复杂的授权规则——以及 Taproot 如何让这些复杂规则在链上"隐形"。

16.1 多签：m-of-n 授权

m-of-n 多签的意思是：一共有 n 把钥匙，任意 m 把就能花这笔钱。最常见的组合：

配置场景
2-of-2夫妻共同账户、交易所冷热分离（一笔交易需要两个系统同时签名）
2-of-3最实用：三把钥匙分处三地，丢一把不影响使用，丢两把才丢币
3-of-5公司金库：五个高管各持一把，任意三人可动用
1-of-2实际上等于"或"逻辑：两把钥匙任一即可

早期的多签脚本长这样（以 2-of-3 为例）：

2-of-3 多签锁定脚本asm
OP_2 <pubkey_A> <pubkey_B> <pubkey_C> OP_3 OP_CHECKMULTISIG
OP_CHECKMULTISIG 的一个著名 bug

这个操作码有一个从比特币诞生第一天就存在的 bug：它会多弹出一个栈元素（历史原因，疑似最初实现时的 off-by-one）。

为了不破坏兼容性，这个 bug 一直保留到现在。所以所有多签的解锁脚本都必须在最前面放一个 OP_0（或任意值）来"喂"给这个 bug。你在区块浏览器上看到多签交易的 scriptSig 以 OP_0 开头，就是这个原因。

这是一个很好的例子：在共识系统里，bug 一旦被全网接受，就变成了规范。

16.3 Taproot：让复杂合约看起来像普通转账

2021 年 11 月激活的 Taproot（BIP340/341/342）是比特币脚本能力最大的一次升级。它解决了三个问题：

旧问题Taproot 的解法
隐私：多签和复杂合约在链上一目了然，等于公开你的财务安排 MAST（Merkle 化抽象语法树）：只暴露实际用到的那条分支，其他分支永远隐藏
体积：Schnorr 签名前，多签要列出所有公钥和签名，交易很大 密钥聚合：多个公钥可以聚合为一个，多签的链上体积和单签一样

16.4 Schnorr 签名的关键优势

Taproot 用 Schnorr 签名取代了 ECDSA。它有一个 ECDSA 不具备的性质：线性可加性。

密钥聚合原理plain
Alice 私钥 a，公钥 A = a·G
Bob   私钥 b，公钥 B = b·G

聚合公钥：P = A + B = (a + b)·G
聚合签名：s = sa + sb

验证时，只需检查 s·G == P 是否成立。

关键：链上只出现一个公钥 P 和一个签名 s。
      外界完全看不出这是单签还是 2-of-2 多签。
为什么这很重要

在 Taproot 之前，"安全"和"隐私"是矛盾的：你用多签保护资产，就等于向全世界宣布"这里有大额资产，而且是个多签"。

Taproot 之后，最安全的方案同时也是最隐私的方案——因为复杂合约在链上和最简单的单签转账长得一模一样。这让安全性不再需要付出隐私代价。

第 18 章要讲的闪电网络，就是靠时间锁 + 多签 + 哈希锁组合实现的。它的核心机制是：

Chapter 17SegWit 与扩容之争

2015—2017 年，比特币社区爆发了历史上最激烈的争论。理解它，就理解了比特币的治理方式。

17.1 问题的起点：区块满了

中本聪在 2010 年加了一个 1 MB 的区块大小上限。他当时说是"临时措施"，但一直没改。 随着使用量增长，区块逐渐被填满，交易开始排队，手续费上涨。

2017 年前后，mempool 里堆积了十几万笔待确认交易，手续费一度飙升到几十美元一笔。争论由此爆发。

17.2 两种扩容路线

大区块派小区块 + 二层派
核心主张直接把区块上限调大（2MB、8MB、甚至 32MB）保持区块小，优化数据结构，把交易移到链下
理由链上容量是瓶颈，扩容最直接；手续费太高会赶走用户大区块会让全节点成本上升，导致节点数减少，去中心化受损
代价需要硬分叉；节点存储和带宽要求上升短期体验改善有限；二层方案复杂度高、成熟需要时间
结果2017 年 8 月分叉出 Bitcoin Cash（BCH）SegWit 于 2017 年 8 月激活，成为主链路线
争论的本质不是技术，是价值观

双方都能算清技术账，分歧在于"比特币是什么"：

大区块派认为比特币应该是一种支付系统——必须便宜、快速、人人可用。

小区块派认为比特币应该是一种结算层和储值资产——最重要的属性是不可篡改和抗审查，为此可以牺牲链上吞吐量，把高频支付放到二层。

这不是"谁对谁错"，而是两种不同的产品定位。最终市场选择了后者：BCH 分叉后市值一路下滑，主链继续主导。

17.3 SegWit 做了什么

SegWit（Segregated Witness，隔离见证）的核心思路很巧妙：把签名数据从交易里"隔离"出来。

17.4 交易延展性：一个被忽视的致命 bug

在 SegWit 之前，有一个问题困扰了比特币多年：第三方可以修改一笔交易的签名，使 txid 改变，但交易依然有效。

原因是 ECDSA 签名具有"可塑性"——(r, s) 和 (r, N−s) 都是合法签名。 攻击者可以翻转 s，重新构造一笔内容相同但 txid 不同的交易。

这在单笔转账里影响不大，但在链式交易里是致命的：

延展性攻击plain
Alice 广播交易 A（txid = abc123）
Alice 立即构造交易 B，花掉 A 的输出（引用 abc123）

攻击者收到 A 后，篡改签名得到 A'（txid = def456，内容相同）
全网最终确认的是 A'

→ Alice 的交易 B 引用了一个不存在的 txid abc123
→ B 永远无法确认，资金卡死

在闪电网络里，这意味着"通道开启交易"可能无法按预期上链，
整个二层协议的信任基础就崩了。

SegWit 把签名移到 txid 计算范围之外，彻底解决了这个问题。

17.5 这场争论教会我们什么

比特币的治理没有"最终裁决者"

扩容之争持续了两年多，没有董事会、没有 CEO、没有投票机制能一锤定音。最终的解决方式是：

分歧无法弥合时，就分叉。每一方都可以带走代码、继续自己的路线，市场用脚投票决定哪条链有价值。

这种机制看起来低效、混乱、充满争吵，但它有一个重要优点：没有人能单方面改变规则。包括中本聪自己——他在这场争论开始前就已经离开了。

本章要点
  • 扩容之争的本质是比特币的定位之争：支付系统 vs 结算层。
  • SegWit 把签名数据隔离计价，权重打 1 折，有效容量提升约 1.8 倍。
  • SegWit 顺带修复了交易延展性——这是闪电网络的前置条件。
  • 比特币没有最终裁决者，分歧的出口是分叉 + 市场选择。

Chapter 18闪电网络

如果每笔咖啡交易都要上链、等十分钟、付几美元手续费，比特币永远无法成为支付工具。闪电网络是答案。

18.1 核心思想：把链上交易变成"开账户"

闪电网络（Lightning Network）的基本单位是支付通道（Payment Channel）。 两个人把资金锁进一个 2-of-2 多签地址，然后在这个通道内无限次转账，每次转账都不上链。

只有两个时刻需要上链：

  • 开通道：双方各存入一笔资金，生成一个多签输出。
  • 关通道：按最后一次双方确认的分配方案结算。

中间的无数次转账，只是在双方之间交换签名过的"新分配方案"。

18.2 从"两人通道"到"全球网络"

如果只能和直接建立通道的人转账，闪电网络的用处很有限。真正的威力来自路由： 你不需要和收款人开通道，只要网络里存在一条从你到他的路径，就能转账。

多跳路由plain
你 → Alice → Bob → Carol → 收款人

每个中间人只是"转发"资金：
  · 你付给 Alice，Alice 付给 Bob，Bob 付给 Carol……
  · 中间人赚取少量路由费（通常几聪）
  · 靠"哈希时间锁合约"（HTLC）保证原子性：
    要么整条路径全部成功，要么全部回滚，不存在"钱扣了但没到"的情况
HTLC：原子性的关键

收款人生成一个随机数 R，把它的哈希 H(R) 告诉付款方。付款方用这个哈希构造 HTLC：

"谁能在 T 时间内拿出 R 的原像，谁就能拿走这笔钱；否则到期退还给我。"

这条规则沿着路径逐跳传播。只有当收款人最终揭示 R 时，整条链上的资金才会依次解锁。 如果超时，全部自动退回。这就是"要么全成，要么全不成"的保证。

· 需要流动性：通道里的资金被锁定，方向有限
· 需要备份：丢失通道状态备份可能导致资金损失
· 复杂度高：路由失败、通道强制关闭等问题需要处理
· 不是完全免信任：大额路由依赖对中间节点的信任假设
最常见的闪电网络误解

"闪电网络是免费的、无限快的，所以比特币能取代 VISA。"

不准确。闪电网络的容量受限于链上锁定的总资金和通道流动性分布。它擅长高频小额支付，但不适合超大额转账（路由会失败，且信任假设变强）。

另外，"不需要在线"这个说法也是错的——收款方离线期间无法收到闪电支付。

18.4 二层方案的一般模式

闪电网络不是唯一，但它是理解所有二层方案的模板。它们的共同套路是：

  1. 把资金锁定在链上的一个多签合约里。
  2. 链下高频更新状态，每次更新都有双方签名。
  3. 用时间锁给"提交旧状态"设置惩罚窗口。
  4. 需要最终结算时，把最后状态提交上链。

理解这个模式后，你就能看懂绝大多数"Layer 2"方案的原理——无论是状态通道、侧链还是 Rollup， 本质都是在"链上保证安全 + 链下提升效率"之间做权衡。

本章要点
  • 支付通道把无数次转账压缩成两次链上交易（开、关）。
  • 路由让任意两人之间可以转账，不必直接建立通道。
  • HTLC 保证多跳转账的原子性：要么全成，要么全不成。
  • 闪电网络擅长小额高频，不适合大额，且收款方必须在线。
  • 所有二层方案的共同模式：链上锁资金 + 链下更新 + 时间锁惩罚。

"""迷你比特币 —— 一个可运行的区块链实现（教学用）"""
import hashlib, json, time

# ============ 1. 密码学原语 ============
def sha256(b): return hashlib.sha256(b).digest()
def dsha(b):   return sha256(sha256(b))          # 双重 SHA256
def b2h(x):    return x.hex() if isinstance(x, bytes) else x

# ============ 2. 交易 ============
class Tx:
    def __init__(self, inputs, outputs, timestamp=None):
        self.inputs  = inputs      # [{"txid":…, "vout":…}]
        self.outputs = outputs     # [{"value":…, "to":…}]
        self.timestamp = timestamp or int(time.time())

    def payload(self, with_sig=True):
        """签名覆盖的内容；算 txid 时不包含签名"""
        ins = [{"txid": i["txid"], "vout": i["vout"],
                "sig": i.get("sig", "")} for i in self.inputs]
        return json.dumps({"in": ins, "out": self.outputs,
                           "ts": self.timestamp},
                          sort_keys=True, separators=(',', ':')).encode()

    @property
    def txid(self):
        return b2h(dsha(self.payload(with_sig=False)))

    def sign(self, secret):
        """简化签名：真实系统用 ECDSA，见第 3 章"""
        import hmac
        for i in self.inputs:
            i["sig"] = hmac.new(secret, self.payload(),
                                 hashlib.sha256).hexdigest()

    def verify(self, secret):
        import hmac
        for i in self.inputs:
            want = hmac.new(secret, self.payload(), hashlib.sha256).hexdigest()
            if i.get("sig") != want:
                return False
        return True

# ============ 3. 区块 ============
class Block:
    def __init__(self, index, prev_hash, txs,
                 timestamp=None, nonce=0, difficulty=3):
        self.index = index
        self.prev_hash = prev_hash
        self.txs = txs
        self.timestamp = timestamp or int(time.time())
        self.nonce = nonce
        self.difficulty = difficulty

    @property
    def merkle_root(self):
        layer = [bytes.fromhex(t.txid) for t in self.txs] or [b"\x00"*32]
        while len(layer) > 1:
            if len(layer) % 2: layer.append(layer[-1])
            layer = [dsha(layer[i] + layer[i+1])
                     for i in range(0, len(layer), 2)]
        return b2h(layer[0])

    def header(self):
        return (f"{self.index}|{self.prev_hash}|{self.merkle_root}|"
                f"{self.timestamp}|{self.difficulty}|{self.nonce}").encode()

    @property
    def hash(self):
        return b2h(dsha(self.header()))

    def mine(self):
        """工作量证明：不断改 nonce 直到哈希满足前导零要求"""
        target = "0" * self.difficulty
        while not self.hash.startswith(target):
            self.nonce += 1
        return self

# ============ 4. 链 ============
class Chain:
    def __init__(self, difficulty=3):
        self.difficulty = difficulty
        self.blocks = []
        self.utxo = {}          # "txid:vout" -> {"value":…, "to":…}
        self._genesis()

    def _genesis(self):
        cb = Tx([], [{"value": 50_00000000, "to": "satoshi"}])
        g = Block(0, "0"*64, [cb], difficulty=self.difficulty).mine()
        self.blocks.append(g)
        self._apply(g)

    def _apply(self, block):
        for tx in block.txs:
            for i in tx.inputs:                  # 消耗输入
                self.utxo.pop(f"{i['txid']}:{i['vout']}", None)
            for n, o in enumerate(tx.outputs):       # 创建输出
                self.utxo[f"{tx.txid}:{n}"] = {"value": o["value"],
                                             "to": o["to"]}

    def balance(self, addr):
        """余额 = 该地址名下所有 UTXO 之和（账本里没有这个字段）"""
        return sum(u["value"] for u in self.utxo.values()
                   if u["to"] == addr)

    def add_block(self, txs):
        prev = self.blocks[-1]
        b = Block(len(self.blocks), prev.hash, txs,
                  difficulty=self.difficulty).mine()
        assert b.prev_hash == prev.hash          # 哈希链校验
        self.blocks.append(b)
        self._apply(b)
        return b

    def is_valid(self):
        for i in range(1, len(self.blocks)):
            cur, prev = self.blocks[i], self.blocks[i-1]
            if cur.prev_hash != prev.hash: return False
            if not cur.hash.startswith("0" * cur.difficulty):
                return False
        return True

失败了。原因链条是这样的：

  1. 改了 coinbase 金额 → 交易内容变了 → txid 变了。
  2. txid 变了 → merkle_root 变了。
  3. merkle_root 变了 → 块 1 的区块头变了 → 块 1 的哈希变了。
  4. 块 1 的哈希变了 → 块 2 里存的 prev_hash 对不上了。

在真实比特币里，攻击者还需要重新挖出块 1 之后的所有区块，并且要跑得比全网诚实算力更快。 这就是第 2 章讲的"生产贵、验证便宜"在起作用。

Chapter 20二十个常见误区

最后，把流传最广的错误认知集中清理一遍。每一条都对应前面某一章的知识。

关于技术原理

① "比特币是一个加密系统，交易内容是加密的" 错。比特币用签名，不是加密。交易内容完全公开。详见第 3.6 节。
② "区块链就是把数据分成一个个块连起来" 不完整。关键不是"连起来"，而是每个块的哈希包含前一个块的哈希，使得改动历史需要重做后续全部工作量。详见第 4 章。
③ "钱包里存着比特币" 错。币只存在于区块链上。钱包里存的是私钥——能证明你有权花费那些 UTXO 的凭证。详见第 14 章。
④ "我有 1 个比特币，所以账本上有一条记录写着 1 BTC" 错。你可能有 5 个 UTXO，分别是 0.3、0.3、0.2、0.1、0.1。账本上没有"余额"这个字段。详见第 5 章。
⑤ "比特币地址就是一个账号" 错。地址只是锁定脚本的人类可读编码，可以无限生成，不绑定任何身份，也不含任何密钥信息。详见第 8 章。
⑥ "挖矿是在解复杂的数学题" 不准确。挖矿是暴力试错，不是"解题"。它没有任何智力成分，纯粹是比谁的哈希算力大。详见第 10 章。
⑦ "挖矿是在验证交易" 只对一半。所有全节点都在验证交易。矿工的额外工作是：选择打包哪些交易、并做工作量证明。详见第 9 章。
⑧ "矿工可以随便给自己发币" 错。coinbase 交易金额有硬上限：区块补贴 + 本块手续费。超发的块会被所有全节点直接丢弃。详见第 10.3 节。
⑨ "最长链原则" 表述不准确。准确规则是累计工作量最大的链，不是块数最多的链。详见第 12.1 节。
⑩ "6 个确认是协议规定" 错。这是行业惯例，不是协议规则。协议层面 1 个确认就算数，只是被重组风险较高。详见第 12.2 节。

关于安全

⑪ "51% 算力就能偷走别人的币" 错。算力不能伪造签名。51% 攻击能做的是双花自己的交易和审查交易，不能偷币、不能增发。详见第 12.4 节。
⑫ "量子计算机很快会破解比特币" 时间尺度被夸大了。Shor 算法理论上能破解 ECDSA，但需要数百万个稳定量子比特，目前离这个目标还很远。而且比特币可以软分叉升级到抗量子签名方案。更现实的短期风险是：长期未动过的、公钥已暴露的地址（如 P2PK 输出）会最先受影响。详见第 3 章。
⑬ "用强密码就能保护钱包" 错。私钥是一个 256 位随机数。密码只是加密钱包文件的额外一层，如果密码很弱，攻击者可以离线暴力破解。真正的安全来自私钥本身的随机性和离线保存。
⑭ "把助记词分几份存在不同地方更安全" 错。分片降低了每一片的信息量，但没有降低整体泄露风险，还增加了丢失风险。正确做法是完整备份多份，或使用 Shamir 秘密分享。详见第 14.4 节。
⑮ "交易确认了就不会被撤销" 不严谨。1 个确认的交易理论上仍可能被重组，只是概率极低。确认数越多越安全。详见第 12.2 节。

关于使用

⑯ "比特币转账手续费是按金额比例收的" 错。手续费按字节数收，不按金额。转 1 BTC 和转 0.001 BTC，如果输入输出结构相同，手续费完全一样。详见第 13.3 节。
⑰ "0 确认就可以放心收款" 危险。付款方可以用 RBF 把交易替换掉，尤其在手续费上涨时。大额收款应等至少 1—6 个确认。详见第 13.4 节。
⑱ "比特币是匿名的" 错。比特币是伪匿名：地址不直接对应身份，但所有交易永久公开可查。一旦某个地址被关联到现实身份，全部历史都会暴露，还能通过交易图分析推断出关联地址。详见第 14.3 节。
⑲ "闪电网络让比特币能取代 VISA" 过于乐观。闪电网络擅长小额高频，但容量受限于链上锁定的资金和流动性分布，不适合超大额转账，且收款方必须在线。详见第 18.3 节。
⑳ "丢了私钥可以找客服/开发者找回" 不可能。没有中心化机构持有你的密钥，没有任何人能帮你恢复。这正是"自我托管"的代价。详见第 14 章。
最后一条建议

如果你是第一次真正使用比特币，请遵循这个顺序：

1. 先只放一笔你完全损失得起的金额，走完"买入 → 转到自己的钱包 → 转出"的完整流程。
2. 亲手抄写助记词，然后真的做一次恢复测试（用新设备或重置钱包软件，从助记词恢复，确认地址一致）。
3. 确认恢复流程没问题之后，再考虑增加金额。
4. 永远记住：链上交易不可逆，没有客服，没有撤销键。

症状一笔交易的两个输出金额相加超过了 64 位整数上限，发生溢出，凭空产生了 184,467,440,737.09551616 BTC

问题出在哪。比特币的金额用 64 位有符号整数存储，单位是聪。正常范围是 0 到 2,100 万亿聪。代码在检查输出金额时，检查的是单个输出，但把两个输出相加时发生了整数溢出：

溢出原理plain
两个输出都是 9223372036854775808 聪（刚好是 2^63）

单独检查：每个都 > 2100 万亿？ → 是，应该拒绝
但当时的代码检查逻辑有缺陷，没拦住

相加时：
  9223372036854775808 × 2
  = 18446744073709551616
  = 2^64  →  溢出，变成负数或 0

结果：验证通过了，矿工打包了，全网接受了。

怎么修的。中本聪在几小时内发布了修复补丁，并做了一个在比特币历史上唯一一次的决定： 回滚主链。做法是——修好代码后，矿工们在 74638 之前的分叉点上挖出一条新链， 因为这条新链累计工作量更大，全网自动切换了过去，包含坏交易的那条链被抛弃。

这次"回滚"说明了什么

第 12 章我们说过：改历史需要重做后续全部工作量。2010 年之所以能回滚，是因为当时全网算力极小——中本聪一个人几乎就能协调全网。

同样的事情今天做不到，也不应该做。这次回滚是特例，不是惯例。它恰恰证明了比特币的"不可篡改"不是绝对承诺，而是算力规模带来的经济学事实。

教训
  • 金融系统的数字必须用整数，且每次运算都要做范围检查——这也是为什么第 6 章强调"输入里不写金额"。
  • 早期比特币依赖少数人快速响应，这与"去中心化"是矛盾的，但也是它活下来的原因。

危机二 · 2013：两个版本的比特币打起来了

项目内容
时间2013 年 3 月 11 日，区块高度 225430
症状网络分裂成两条链：跑 0.8 版本的节点和跑 0.7 版本的节点各认一条

问题出在哪。Bitcoin 0.8 换用了新的数据库引擎（LevelDB）来索引交易。 有一笔交易用了当时非标准的锁定脚本，0.8 的新代码能正确索引它，0.7 的老代码不能。 结果：0.8 节点接受了这个块，0.7 节点拒绝了它。

怎么修的。矿池运营者们做了一个反直觉的决定：主动降级回 0.7。 他们的算力回到了老链上，让老链重新变长，网络恢复一致。然后开发者花了几个月修好 0.8 的问题，再重新升级。

这次事故带来的最大改变

共识代码的审查文化。在此之前，比特币的开发更像普通开源项目；在此之后，形成了今天的规矩：

· 任何触碰共识规则的代码，必须有大量测试向量（已知输入必须得到已知输出）
· 必须有多位独立审阅者，且审阅者要真正读懂每一行
· 宁可保守，不可激进——"能不改就不改"成为共识

你今天看到的 Bitcoin Core 那种近乎偏执的谨慎，源头就是 2013 年 3 月的这一天。

危机三 · 2014：Mt.Gox 与"不是你的私钥，就不是你的币"

项目内容
时间2014 年 2 月
规模约 85 万 BTC 失踪（其中约 75 万属于用户），当时占流通量约 7%

问题出在哪。Mt.Gox 曾经处理全球约 70% 的比特币交易量，但它本质上是一家账务混乱的公司： 内部用 txid 做记账索引，而当时 txid 是可以被第三方篡改的（交易延展性，见第 17.4 节）， 导致账目对不上；加上冷热钱包管理混乱、内部盗窃、长期无人审计，最终资不抵债。

这件事最容易被误解的地方

很多人把 Mt.Gox 说成"比特币的失败"。恰恰相反——比特币协议本身没有出任何问题， 每一枚币在链上都有清晰记录。出问题的是把币交给别人保管这件事。

这次事件催生了两个长期影响：
① "Not your keys, not your coins" 成为行业第一铁律（第 14 章）。
② 交易延展性从一个"理论上的小毛病"升级为"必须修的严重问题"，直接推动了 SegWit。

危机四 · 2015—2017：扩容僵局与"用户起义"

这段历史第 17 章已经详细讲过，这里只补充最关键的一个机制创新：UASF（用户激活软分叉）。

项目内容
时间2017 年 8 月 1 日
背景矿工和矿池通过"纽约协议"要求先扩容再激活 SegWit，僵持不下
做法BIP148 规定：从 8 月 1 日起，运行该版本的节点拒绝任何不 signaling SegWit 的区块
结果矿工面临风险——如果继续拒绝，他们挖的块会被这部分节点抛弃。最终矿工妥协，SegWit 在 8 月 24 日锁定
UASF 揭示的权力结构

在这次事件之前，很多人认为"矿工决定比特币的未来"。UASF 证明了这个认知是错的：

矿工决定打包顺序，但全节点运行者决定什么规则是有效的。

矿工挖出一个不满足节点规则的区块，即使算力占 90%，节点也会直接丢弃它——矿工的区块奖励就白挖了。所以矿工最终必须服从节点的规则。

这是比特币治理的核心：权力属于那些真正运行验证软件的人，而不是拥有算力或资金的人。

危机五 · 2023—2026：铭文之争——当区块空间被"非金融数据"挤占

项目内容
起点2023 年 1 月，Ordinals 协议出现，把图片、文本等数据写进交易的见证字段
后果区块空间被大量占用，手续费一度长期高企；矿工收入增加，普通转账用户成本上升
反制2026 年 2 月 BIP-110 进入 BIP 库，主张临时限制非金融数据的字段大小
结局2026 年 8 月，支持方尝试运行少数链分叉，只挖出 2 个区块即告失败

为什么这次和以往不一样。前面几次危机，社区能就"什么是错的"达成一致（溢出是错的、延展性是错的、区块满了是问题）。这次不行，因为双方的价值判断根本对立：

立场核心论点
限制方 区块空间是稀缺的公共资源，应该用于金融结算。用极低成本存储图片会推高所有人的交易成本，属于"公地悲剧"。
自由方 只要能付得起手续费，写什么都是合法的。任何"内容审查"式的规则都是滑坡——今天禁图片，明天可能禁别的。抗审查是比特币的第一属性。
BIP-110 的失败方式很值得玩味

它没有被打压、没有被封杀，而是——没人跟。少数链分叉挖出 2 个块就停了，因为矿工算了一下：跟着这条链挖不赚钱。

这正是第 12 章"分叉 + 市场选择"机制在起作用：你不需要说服任何人放弃，你只需要带着支持者自己走，然后市场告诉你答案。

这种"退出机制"看起来低效，但它比任何投票都更接近真实意愿——因为参与者要用钱和算力投票，而不是动嘴。

危机六 · 进行中：量子计算机的倒计时

这不是"已经发生的事故"，而是一个所有人都知道会来、但不知道什么时候来的问题。

项目内容
威胁Shor 算法理论上能在多项式时间内从公钥反推私钥，从而破解 ECDSA
现实门槛需要数百万个稳定的物理量子比特；目前离这个目标还有几个数量级的差距
最先受害的公钥已经暴露在链上的地址——尤其是早期 P2PK 输出和地址复用过的地址
相对安全的从未花费过的 P2PKH 地址（只暴露了公钥哈希，没暴露公钥）
进度2026 年 2 月 BIP-360（P2MR 输出类型）合并进 BIP 库；已有团队在量子测试网上部署实现

为什么这件事特别难办。技术方案本身不难——换一套抗量子签名（如 ML-DSA / SLH-DSA）就行。难的是迁移过程：

迁移的两难

链上有大约 670 万 BTC 存放在易受量子攻击的地址里（包括早期从未动过的币）。这些币的主人可能已经弄丢了私钥，也可能已经不在人世。

方案 A：不管它们。那么未来的量子攻击者可以直接拿走这 670 万 BTC，获得一笔巨大的攻击预算。
方案 B：冻结它们。通过软分叉宣布这些地址作废。这被批评者称为"比特币史上最专制的软分叉"，因为它侵犯了财产权。

这个争论的深层问题是：比特币的"绝对财产权"是无限期的吗？当"保护系统"和"保护个人产权"冲突时，哪个优先？

六次危机的共同模式
  • 危机几乎都来自"边界情况"：溢出、实现差异、脚本非标准、字段被滥用——都是正常路径之外的角落。
  • 修复方式永远是软分叉优先：能不分裂就不分裂。
  • 每次都留下制度遗产：溢出→整数检查；2013→共识审查文化；Mt.Gox→自托管；扩容→UASF；铭文→分叉退出机制。
  • 技术问题能解决，价值冲突不能。量子迁移和铭文之争都属于后者。

Chapter 23从危机里长出的技术

每一次危机过后，比特币都会长出一个新零件。这一章把这些零件摆出来，并回答那个关键问题：为什么它们是合理的？

23.1 先搞清 BIP 是什么

BIP（Bitcoin Improvement Proposal，比特币改进提案）是一份公开的技术文档， 描述一个变更的动机、规格、兼容性影响和参考实现。它不是命令，也不是投票选项——它只是一份说明书。

一个 BIP 从想法变成全网规则，要走过这样一条路：

BIP 编号不是版本号

BIP 是按提交顺序编号的，不代表重要性或优先级。BIP 39（助记词）和 BIP 340（Schnorr）之间隔了三百多个编号，但两者都很重要；也有很多 BIP 永远停留在 Draft 状态，从未被实现。

下面逐个说清楚它们为什么 make sense。

① P2SH：把责任从付款方转移到收款方

在 P2SH 之前，如果你想用一个 2-of-3 多签收款，你得把整个长脚本给付款方，让他拼进交易里。 问题很明显：脚本很长（地址很长，容易抄错），而且付款方要为你设计的复杂逻辑负责——他抄错一个字，钱就没了。

P2SH 的做法是：地址里只放脚本的哈希（20 字节）。付款方只需要知道一个短地址；真正的脚本由收款方在花费时提供。

为什么这个设计合理

· 责任归位：谁设计的脚本，谁负责提供和验证它。
· 地址短：20 字节哈希 → 以 3 开头的短地址。
· 向后兼容：老节点不需要理解新脚本，只需要验证哈希是否匹配——所以能做软分叉。
· 为未来留门：任何新脚本类型都能塞进 P2SH 容器里，不需要再次改共识。

② SegWit：用"计价"代替"限制"

面对"区块太小"的问题，有两种思路：把上限调大（硬分叉），或者改变计价方式（软分叉）。SegWit 选了后者，而且顺手修了一个致命 bug。

为什么这个设计合理

· 不改变区块上限的数值，只是把签名数据的权重打 1 折。老节点看到的区块仍然"≤1 MB"，所以是软分叉。
· 实际容量提升约 1.8 倍，但不需要说服所有人同时升级。
· 修掉了交易延展性——签名不再参与 txid 计算。这一步没有它，闪电网络根本做不出来。
· 代价是代码变得很别扭：见证数据被塞在一个老节点会忽略的位置，导致后来很多实现细节都很反直觉。这是"软分叉优先"的必然代价。

③ PSBT 与 Miniscript：不改共识，只改工具

这两项很特别——它们完全不需要软分叉，因为它们只改变"钱包软件怎么工作"，不改变任何验证规则。

解决什么为什么合理
PSBT
部分签名交易		 以前"构造交易"和"签名"必须在同一个软件里完成。这意味着一台冷钱包必须联网，或者你必须把私钥导入联网设备——两者都不可接受。 PSBT 把交易变成一个可以离线传递的文件：联网电脑构造 → U 盘带到冷钱包 → 冷钱包签名 → U 盘带回 → 广播。私钥永不联网，但流程完全标准化，不同厂商的钱包可以互操作。
Miniscript 比特币脚本是汇编级的。手写一个"2-of-3 且 90 天后可退款"的策略，很容易把条件写反——而写错的脚本会把钱永久锁死。 Miniscript 提供一个可分析的中间表示：钱包可以自动检查"这个脚本在任何情况下都有人能花吗""花费需要多少签名""最坏情况手续费是多少"。把"手写汇编"变成"编译目标"，这是工程上的正确做法。

④ Taproot：让"复杂"不再等于"可疑"

Taproot 的合理性在第 16 章讲过，这里只强调它的设计哲学：

Taproot 最重要的不是功能，是它消除的矛盾

在 Taproot 之前，安全性和隐私性是对立的：你用多签保护资产，就等于在链上挂个牌子写"这里有大钱，而且是多签"。

Taproot 之后，最安全的方案同时也是最隐私的方案——因为复杂合约在链上和最简单的单签转账长得完全一样。

一个升级能做到"不牺牲任何东西就同时改善安全、隐私、体积"，这是极少见的。这也是它能在 Taproot 激活时几乎无争议的原因。

⑤ BIP324：把 P2P 流量藏起来

比特币节点之间的通信一直是明文的。这意味着：ISP 可以识别出"这个 IP 在跑比特币节点"， 从而实施封锁；中间人可以看到你广播了哪些交易，并据此推断你的 IP 与哪些地址相关。

BIP324 引入了加密传输（不是共识变更，只是传输层升级）：

  • 流量看起来像随机字节，无法被特征识别
  • 防中间人篡改
  • 还能降低带宽开销（省略了冗余的校验和字段）
为什么它合理

它不改变任何共识规则——即使一半节点用加密传输、一半用明文，网络照样正常工作。这种"只改善网络层、不触碰共识"的变更，是比特币里阻力最小的升级类型。

23.3 为什么这些升级都 make sense：五条共同特征

把上面六项放在一起看，会发现它们遵循一套非常一致的取舍原则。这套原则本身就是比特币的"设计哲学"。

原则含义反例（被拒绝的设计）
① 收紧规则，不放宽 新规则必须是旧规则的子集。这样老节点仍能接受新块 → 软分叉 → 不分裂网络。 把区块上限从 1 MB 改成 8 MB 是放宽，必须硬分叉 → 2017 年 BCH 的路线。
② 不改变货币属性 总量、发行速度、减半节奏——这些永远不动。 任何提议修改 2100 万上限的方案，连讨论的余地都没有。
③ 保持验证成本可预测 脚本不能图灵完备，不能有循环。节点必须能在有限时间内判断一个区块是否合法。 在比特币上跑任意智能合约（以太坊路线）会让验证成本不可预测，导致节点门槛上升。
④ 优先改善"结构性缺陷" 先修 bug，再谈功能。SegWit 修延展性、BIP54 修共识边界，都比新功能优先级高。 把新操作码和 bug 修复捆在一起推进，会被质疑"夹带私货"。
⑤ 能不上共识就不上共识 钱包层能解决的（PSBT）、工具层能解决的（Miniscript）、网络层能解决的（BIP324），都不要碰共识规则。 共识变更成本极高、风险极大、协调周期以年计。能绕开就绕开。
一个反直觉的结论

比特币的升级速度很慢，这常被批评为"僵化"。但从另一个角度看：

一个金融基础设施的价值，恰恰在于它的规则不容易变。

你愿意把钱放在一个"社区觉得好就可以改规则"的系统里吗？比特币的保守，不是工程能力的缺陷，而是它作为"货币"这一用途的核心功能。

换句话说：如果比特币变得容易升级，它就不再是比特币了。

本章要点
  • BIP 只是说明书，不是命令；从想法到规则要经过数年评审和测试网验证。
  • P2SH 转移责任、SegWit 修延展性、PSBT 解耦签名流程、Miniscript 防脚本写错、Taproot 消除安全与隐私的矛盾、BIP324 隐藏 P2P 流量。
  • 所有成功的升级都遵循：收紧规则、不动货币属性、保持验证成本可预测、优先修 bug、能不上共识就不上共识。
  • 升级慢不是缺陷，而是"作为货币"这一用途的功能要求。

Chapter 24分叉、山寨币与二层

比特币十七年历史里，"从它身上诞生的新东西"远不止协议升级。这一章把三类东西分开讲清楚，并给出一个判断它们是否合理的框架。

24.1 三类"新东西"

类别是什么例子与比特币的关系

24.2 硬分叉币：为什么"复制代码"没用

2017 年的扩容之争直接催生了一批分叉币。它们的逻辑很简单：既然主链不肯改，我们改一个自己的版本。

币种时间核心主张结局
Bitcoin Cash 2017-08 区块调到 8 MB，后来又提到 32 MB，坚持"比特币应该是支付系统" 初期有热度，之后算力和市值持续下滑
Bitcoin SV 2018-11 从 BCH 再分叉，主张"回归中本聪原始设计"，区块上限 128 MB 进一步边缘化
Bitcoin Gold 2017-10 改用抗 ASIC 的 PoW 算法，让普通显卡也能挖 多次被 51% 攻击（第 12.4 节）
分叉能复制什么，不能复制什么

能复制：代码、历史账本、甚至早期的持币地址。
不能复制：算力、开发者社区、交易所流动性、商户接受度、品牌认知、以及最重要的——网络效应。

这解释了一个看起来奇怪的现象：BCH 的区块上限是比特币的 32 倍，理论上"更好用"，但它的算力只有比特币的千分之几。因为安全性正比于算力（第 12.4 节），算力低意味着攻击成本低——Bitcoin Gold 被反复 51% 攻击就是证明。

结论：在货币这件事上，"技术上更优"远远不够。

24.3 独立设计的币：它们各自解决了什么真问题

与"复制代码的分叉币"不同，有一类币从一开始就选择了不同的技术路线。它们更值得认真评估。

币种年份它试图解决的问题为什么这个方向是合理的
Litecoin 2011 比特币出块 10 分钟太慢，且早期挖矿门槛高 出块 2.5 分钟确实更快。但它用 Scrypt 抗 ASIC 的初衷失败了——最终还是被 ASIC 化。这说明抗 ASIC 是个会随时间失效的目标。
Monero 2014 比特币是伪匿名的，交易图分析能扒出真实身份 用环签名 + RingCT 隐藏发送方、接收方和金额。这是比特币结构上无法提供的属性——因为比特币的账本必须公开可验证，而 Monero 用密码学在不公开明细的前提下保证不超发。这是真正的问题、真正的解法。
Zcash 2016 同上，但用零知识证明实现 zk-SNARK 能让"金额合法"这件事在不公开金额的情况下被验证，理论更优雅。代价是：早期需要"可信设置"，且可选隐私意味着大多数人不用——当隐私是可选的时候，用它的人就会暴露自己。
Ethereum 2015 比特币脚本太弱，做不了复杂应用 账户模型 + 图灵完备 + 全局状态，确实能表达比特币表达不了的东西。但它付出了明确的代价：状态膨胀（节点必须保存全部合约状态）、验证成本不可预测（一笔交易可能消耗极多计算）、以及更复杂的攻击面。

24.4 判断一个币是否 make sense：三个条件

面对任何一个新币，不要看白皮书里的愿景，问这三个问题：

最常见的失败模式

"我们改进了 X，所以我们应该取代比特币。"

这句话的问题在于：货币不是技术竞赛，而是协调博弈。比特币的价值很大一部分来自"最多人认可它"。一个新币即使技术上全面更优，也要面对一个残酷的问题——为什么要让全世界同时换一次账本？

历史上，这个问题的答案通常是：不需要。除非新东西提供了质变（比如真正的隐私），否则人们没有理由承担切换成本。

24.5 比特币自己的二层与生态

比"新币"更有意思的，是在比特币之上长出来的东西。它们不发行新币，用的就是 BTC。

项目时间做了什么为什么 make sense
闪电网络 2018 起 把高频小额支付搬到链下，链上只做开/关通道 它承认了"链上区块空间永远稀缺"这个前提，然后用二层解决容量问题。是唯一被广泛采用的二层方案。（第 18 章）
Liquid / Rootstock 2018 / 2019 联邦侧链，提供更快的结算和智能合约能力 代价是"联邦"——一组已知的签名者控制资产进出。它用信任换性能，所以信任假设必须被公开说清楚。
Ordinals / 铭文 2023 把图片、文本写进见证数据，给每个聪编号 技术上利用了 SegWit 的见证折扣。它引发了第 22 章的"公地悲剧"之争——能付手续费 ≠ 应该占用空间。
Runes / BRC-20 2023—2024 在比特币上发行同质化代币，比铭文更节省空间 用 UTXO 模型原生地表达代币，比在见证数据里塞 JSON 更"比特币式"。但仍会占用区块空间。
BitVM / BitVM2 2023 / 2026 用"挑战—响应"博弈，在比特币上验证任意计算，不需要软分叉 见下一节。这是近年来最值得注意的技术方向。

24.6 为什么 BitVM 特别值得注意

BitVM 解决的是一个长期被认为"必须改共识才能做"的问题： 如何在比特币上验证一段任意复杂的计算？

核心思路

不在链上执行计算，而是：

1. 计算者在链下算出结果，并给出承诺（"我认为结果是 R"）。
2. 任何人都可以挑战这个结果，指出具体哪一步算错了。
3. 比特币脚本只需要能验证一步计算（一个很小的逻辑门）。
4. 如果挑战成功，计算者的押金被罚没；如果无人挑战成功，结果被接受。

关键洞察：验证一步 ≠ 验证全部。只要能把"找错误"这件事定位到具体一步，就只需要极小的脚本能力。

为什么它合理：

  • 不需要软分叉。它只用比特币现在就有的脚本能力 + 博弈论。这绕开了第 25 章要讲的"激活方法论僵局"。
  • 信任假设是可量化的：只需要"存在一个诚实的挑战者"（1-of-n 假设），而不是"某组签名者都诚实"。
  • 把成本转移到链下：正常情况下一分钱不花，只有争议才上链。这与闪电网络的哲学一致。
  • 它承认了自己的弱点：争议要花区块空间，如果争议期间手续费暴涨，挑战者可能被"价格挤出"。这是明确的、可管理的风险，而不是隐藏的假设。
但要小心叙事

BitVM 常被宣传为"比特币终于有智能合约了"。这不准确。

它的定位是为桥和 Rollup 提供验证机制，不是让普通用户在比特币上跑应用。而且它有真实的工程复杂度和经济风险（争议成本、押金规模、挑战窗口）。

判断一个新技术的成熟度，有一个简单标准：看它的支持者是否愿意主动说出它的缺点。如果宣传里只有优点，那说明还没到能上生产的阶段。

本章要点
  • 分叉能复制代码，不能复制算力、开发者、流动性和网络效应。
  • 评估一个币：① 解决比特币结构上做不到的事？② 没牺牲核心属性换性能？③ 不需要信任某个团队？
  • 货币是协调博弈而非技术竞赛，"技术更优"不足以取代既有的网络效应。
  • 比特币的二层分两类：用信任换性能的（Liquid）和用博弈论换功能的（闪电、BitVM）。后者的信任假设更弱。
  • BitVM 的价值在于：不用改共识也能获得可编程性，绕开了治理僵局。

Chapter 25未来十年

最后这一章不讲答案，讲问题。比特币面前还摆着几个没有解的难题，它们决定了它下一个十年会变成什么样。

25.1 悬案一：契约（Covenants）

契约是一种能限制这笔钱未来怎么花的脚本能力。 现在的比特币脚本只能规定"谁能花"（签名），契约能规定"花的时候必须满足什么条件"。

提案编号能力状态（2026）
CTV
CheckTemplateVerify		 BIP119 限制花费交易必须符合预先承诺的模板 有激活客户端和 signaling 窗口，但矿工支持率极低
BIP448 组合
TEMPLATEHASH + CSFS + INTERNALKEY		 BIP448 等 Taproot 原生的可重绑定交易方案，更现代的组合 Draft，已在 signet 测试网激活供开发者测试
OP_CAT BIP347 拼接两个栈元素，能构造更复杂的验证逻辑（包括某些零知识证明验证） 规格已完成，但没有激活参数
TXHASH BIP346 更完整的交易自省能力，能提交到同笔交易的其他输入 Draft。作者自己认为审查复杂度显著更高

它能让什么成为可能：

  • 金库（Vault）：钱被偷时有一个"冻结期"，你可以用备用钥匙抢回来。这是目前最被期待的应用。
  • 拥堵控制：预先承诺一笔交易在未来的手续费率，避免手续费飙升时被动。
  • 闪电网络的改进：LN-Symmetry 等构造可以简化通道管理，减少链上交互。
  • 非联邦桥：让 BitVM 式的桥不再依赖预签名委员会。

为什么争议这么大：

支持方理由反对方理由
· 讨论已经持续多年，CTV 早已完成评审，"先上线再迭代"
· 金库等应用能显著提升普通用户的资金安全
· 矿工也在寻找能带动区块空间需求的新叙事		 · 表达力越强，风险面越大——可能引入类似 MEV 的排序套利空间
· 应该先做共识清理（修 bug），再加新功能
· 契约可能扩大审查面：能被限制的用途，也可能被限制不该限制的用途
· 激活方法论本身有争议：Speedy Trial 是为"已经形成压倒性共识"的提案设计的，不适用于有争议的变更
真正的难点不是技术，是流程

各方在技术分歧上其实相当接近（递归还是非递归、最小原语还是通用原语，这些都是可以谈的）。真正卡住的是"怎么决定"这个问题。

2017 年 SegWit 靠 UASF 施压才通过；2021 年 Taproot 用 Speedy Trial 顺利激活。现在每一次讨论激活方法，都会被这两段历史阴影笼罩。

有一个观察很值得记住：在比特币的共识政治里，"持续组织"比"技术更优"更能决定结果。这正是比特币的保守性的来源——也是最难改变的部分。

25.2 悬案二：共识清理 BIP54

与契约提案形成鲜明对比的，是BIP54「共识清理」。它不添加任何新功能，只修复四个历史遗留的边界情况：

修复项问题
时间扭曲 bug难度调整算法里有一个理论缺陷，在极端情况下可被利用来操纵难度
重复 coinbase 交易历史上存在两笔完全相同的 coinbase 交易，破坏了"txid 唯一"的假设
超大脚本某些极大脚本的验证耗时异常，可能导致拒绝服务
旧版本交易回放某些历史交易格式在特定条件下可被重放
为什么它 make sense，而且是"好提案"的模板

· 只收紧规则，不添加功能 → 符合软分叉原则
· 修复的是真实存在的缺陷，不是"我们想要的新东西" → 有明确的问题驱动
· 把多个修复打包，分摊一次软分叉的固定成本 → 工程上更划算
· 反对意见主要是"优先级和时机"，而不是"该不该修" → 争议维度清晰

如果你想知道一个"健康的比特币提案"长什么样，BIP54 就是参照物。

25.3 悬案三：抗量子迁移

这个问题在第 22 章讲过背景，这里说清它的结构性困难。

层面难度
密码学不难。抗量子签名方案（ML-DSA、SLH-DSA）已经标准化，替换即可。
工程中等。新签名体积大很多（几 KB vs 64 字节），会影响区块空间和手续费。
迁移极难。需要几千万用户主动把币转到新地址，而其中一部分人永远不会动。
伦理 / 产权无解。是否冻结约 670 万 BTC 的"僵尸地址"？两个选项都有严重问题。
一个有意思的中间路线

有开发者提出用零知识证明解决迁移难题：让持有易受攻击地址的人，在不暴露私钥的前提下证明"我确实拥有这个地址的私钥"，从而把资金迁到安全地址。

但这个方案本身需要在比特币上验证 STARK 证明——又绕回了契约提案或 BitVM。这说明了比特币技术演进的一个特点：问题之间是互相咬合的，很少能单独解决一个。

25.4 悬案四：矿工收入的转型

第 11 章提过这个问题，2026 年它已经变成了现实压力。

事实含义
2024 年 4 月减半后，区块补贴降到 3.125 BTC矿工收入中"新币"的占比持续下降
2026 年全网算力约 1 ZH/s，难度约 135 T算力仍在增长，意味着竞争更激烈、单位算力收益更低
多家矿企转向 AI / 高性能计算矿场把电力和硬件用于更赚钱的业务——这是理性的商业决策，但也意味着部分算力可能永久离开
铭文高峰期手续费曾经很可观，2026 年已明显回落手续费收入波动极大，不适合作为长期规划基础
这个问题的两种读法

悲观读法：补贴减少 + 手续费不足 → 矿工退出 → 算力下降 → 攻击成本降低 → 安全性下降。

乐观读法：比特币的市值和交易需求会随着采用度增长，手续费市场会自然补上；而且攻击者要攻击的是一个市值更高的系统，收益/成本比未必改善。

两种读法都无法证伪，因为都在预测几十年后的市场。但有一点是确定的：比特币的安全性不再只由"补贴"保证，而越来越依赖"区块空间的市场价值"。这也解释了为什么"区块空间该用来存什么"（铭文之争）不是一个纯粹的技术问题——它直接关系到安全预算。

25.5 悬案五：如何在没有领导者的系统里做决定

把前面四个悬案放在一起，会发现它们卡在同一个地方：决策机制。

比特币的决策机制可以概括成一句话：

没有人能决定，只有人可以选择

比特币没有投票、没有董事会、没有负责人。所谓"决策"实际上是：

1. 有人提出变更，写代码、发文档。
2. 其他人独立评估——不是投票，是各自决定要不要运行这个版本。
3. 如果足够多人运行，新规则生效；如果不够，提案就停在原地。
4. 如果分歧无法弥合，双方可以分叉，各自继续。

这个机制的优点是没有人能单方面改变规则；代价是效率极低，而且"组织能力"往往比"技术优越性"更能决定结果。

25.6 给你的判断清单

读到这里，你已经具备了独立评估一个比特币相关提案的能力。最后留一份清单，下次看到新提案、新币、新协议时，按顺序问这七个问题：

#问题为什么问
1它解决的真实问题是什么？有人因为这个吃过亏吗？没有真实问题驱动的提案，往往是为了技术而技术
2它是收紧规则还是放宽规则？收紧可以软分叉，放宽必须硬分叉——后者成本高一个量级
3它动了货币属性吗？（总量、发行、减半）动了这一条，无论技术多好都不值得讨论
4它让验证成本变得不可预测了吗？节点门槛上升 = 去中心化下降 = 比特币的核心属性受损
5它能在更低的层解决吗？（钱包层、工具层、网络层）能不上共识就不上共识，这是比特币最省成本的路径
6它的支持者主动说出缺点了吗？只讲优点的宣传，说明还没到生产成熟度
7如果分歧无法弥合，退出机制是什么？分叉是比特币的最终仲裁，能分叉说明系统还是活的
写在最后

比特币十七年的历史，本质上是一部在事故中学习、在分歧中妥协、在压力下保守的历史。

它没有变快，没有变得更"先进"，很多看起来该做的事一直没做。但它也从未被攻破、从未被单方面改变规则、从未停止出块。

对于一个要保管人类财富几十年的系统来说，"不出事"比"更强大"重要得多。这就是比特币全部设计的出发点，也是理解它所有"固执"的钥匙。

A.3 延伸阅读

必读原始文档

  • 《Bitcoin: A Peer-to-Peer Electronic Cash System》（2008，中本聪）——9 页的白皮书，比特币的全部思想源头。建议读完本书后再读一遍，感受会完全不同。
  • BIP 仓库（github.com/bitcoin/bips）——所有标准的原始定义。BIP32、BIP39、BIP340 三份文档尤其值得精读。
  • Bitcoin Core 源码（github.com/bitcoin/bitcoin）——重点看 src/validation.cpp（共识规则）、src/script/（脚本引擎）、src/net_processing.cpp（P2P）。

推荐书籍

  • 《Mastering Bitcoin》（Andreas Antonopoulos）——公认最好的技术入门书。本书的很多结构参考了它的思路，但本书更强调"从最简单的概念开始"。该书第 3 版已覆盖 Taproot。
  • 《Programming Bitcoin》（Jimmy Song）——从零实现比特币的库，用 Python。如果你喜欢本书第 19 章的风格，这本会很对胃口。
  • 《The Bitcoin Standard》（Saifedean Ammous）——偏经济学视角，技术内容很少，但能帮你理解"为什么要这样做"。
  • 《Grokking Bitcoin》（Kalle Rosenbaum）——图解丰富，适合视觉型学习者。

动手资源

  • Learn Me A Bitcoin（learnmeabitcoin.com）——交互式的技术教程，可视化做得极好。
  • Blockstream Explorer / mempool.space——区块浏览器。建议打开一笔真实交易，对照本书第 6 章逐个字段看。
  • Bitcoin Core 的 regtest 模式——本地起一条私有链，随便挖、随便试验，不会影响主网。这是最好的实验环境。
  • bitcoinjs-lib / python-bitcoinlib——成熟的库。在写过第 19 章的实现之后再用它们，你会明白每个 API 背后发生了什么。

想追踪演进史与最新提案

  • Bitcoin Optech（bitcoinops.org）——每周一份技术简报，是目前最可靠的比特币工程动态来源。想跟上提案进展，订阅它比看任何新闻都有效。
  • Delving Bitcoin（delvingbitcoin.org）——开发者讨论提案细节的论坛。契约、BitVM、共识清理的原始辩论都在这里。
  • bips.dev / bips.xyz——BIP 的可读版本，比 GitHub 上的原始 Markdown 更适合浏览。
  • Bitcoin Wiki 的 "Value overflow incident" 词条——第 22 章那次事故的一手记录。
  • mempool.space 的 "Mining" 面板——实时看算力、难度、手续费分布，把第 10、11、25 章的抽象数字变成活的曲线。

A.4 写在最后

这本书从一个很朴素的问题开始：两个人怎么记账？我们花了 20 章把这个问题的技术答案一层层拆开：

  • 为了"改不动"，我们用了哈希链。
  • 为了"证明是本人"，我们用了数字签名。
  • 为了"决定顺序"，我们用了工作量证明。
  • 为了"表达条件"，我们用了脚本。
  • 为了"方便使用"，我们用了UTXO、HD 钱包、闪电网络。

这五样东西没有一样是比特币发明的。哈希、签名、P2P、工作量证明，在比特币之前都已经存在多年。 中本聪真正做的事情是：把它们用正确的方式组合在了一起，并加上了难度调整和减半这两个自我调节机制。

所以比特币的精妙之处不在于某个零件有多先进，而在于整体架构在没有任何人维护的情况下，持续运行了十几年。 这是工程上的成就，也是设计思想上的成就。

而第六部分想告诉你的是：这套架构不是一次设计出来的，是十七年里被事故一次次逼出来的。 溢出漏洞逼出了整数检查，交易延展性逼出了 SegWit，多签太显眼逼出了 Taproot， 区块空间被挤占逼出了 BIP-110 的失败和一场还没结束的争论。

理解了这条脉络，你就不再只是"知道比特币怎么工作"，而是能判断它接下来会怎么变、以及哪些变化是不该发生的。 这也是第 25.6 节那份判断清单存在的意义。

如果你读到这里，建议你现在做一件事：打开 mempool.space，找一笔刚确认的交易， 对照第 6 章的字段表，把它的每一个字节都读一遍。那一刻，这本书讲的抽象概念会变成你能看见的具体数据。
