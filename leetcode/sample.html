Chapter 10

Binary Search – The Boundary Rules

The Kernel

There are only two loop shapes and two midpoint formulas. Pick the shape by asking ‘does the answer live in the closed range [lo, hi] or at the boundary where the range collapses?’

Binary search is the most commonly failed easy problem in technical interviews, and it fails for one reason: candidates memorise an implementation rather than the rule that chooses between implementations. They write while lo <= hi, then pair it with hi = mid, and the loop hangs. Or they write lo = mid with the lower midpoint and the loop hangs in the other direction. Both bugs come from the same missing piece of knowledge, and both are trivially avoidable once you have it.

This chapter contains no clever ideas. It contains two loop shapes, two midpoint formulas, and one pairing rule that connects them. Everything else in the binary search family — bounds, rotated arrays, peak finding, binary search on the answer — is a substitution into that frame.

Read the boundary rules below, then close the book and write the template from memory. If you cannot, you have not yet learned this chapter, regardless of how many problems you have solved.

The Boundary Rules

These ten rules are the whole chapter. Rules 1 through 5 are the framework; rules 6 through 10 are the traps.

  1. Shape A — closed range. while lo <= hi: with hi = mid - 1 and lo = mid + 1. Exits with lo == hi + 1. Use when a target may be absent and you must report ‘not found’.
  2. Shape B — half-open, answer is the collapse point. while lo < hi: with hi = mid and lo = mid + 1. Exits with lo == hi == answer. Use for lower bound, upper bound, ‘smallest feasible’, and binary search on the answer.
  3. Midpoint rule. mid = lo + (hi - lo) // 2 is the lower mid. mid = lo + (hi - lo + 1) // 2 is the upper mid.
  4. The pairing rule — memorise this one line. If the branch that moves lo can leave lo == mid (i.e. lo = mid), you MUST use the upper mid. If the branch that moves hi can leave hi == mid (i.e. hi = mid), you MUST use the lower mid. Violating this is an infinite loop, not a wrong answer — which is why it is easy to spot under test.
  5. Equivalently: hi = mid implies lower mid; lo = mid implies upper mid.
  6. Return rule. After Shape A the candidate is lo and it is valid only if lo < n and a[lo] == target. After Shape B lo is the answer unconditionally — Shape B never returns ‘not found’, it returns the insertion point, which is why it is the shape you want for bounds.
  7. Overflow. lo + (hi - lo) // 2 never overflows; (lo + hi) // 2 can in a fixed-width language. Python has arbitrary precision, but write the safe form anyway — interviewers read it as a signal.
  8. Never while lo <= hi with hi = mid. The range does not shrink when hi == mid == lo + 1, and you loop forever.
  9. Never lo = mid without +1. Same failure, other side.
  10. Searching a 2D matrix that is sorted row-wise and column-wise (240) is NOT a binary search over the whole matrix — start at the top-right corner and walk, because that corner is the only cell that is a minimum in one direction and a maximum in the other.

The Template

There are exactly three code shapes. Shape A is for ‘find this exact value and tell me if it is missing’. Shape B is for ‘find the boundary where a predicate flips’. Shape C is Shape B’s mirror, and it exists only because of the midpoint rule: when the branch that moves lo can leave lo == mid, the midpoint must round up.

Memorise Shape B and Shape C as a pair. If you can write both from memory and state why Shape C needs the + 1, you can solve every problem in this chapter and the next four.

# ---------------------------------------------------------- Shape A
# Closed range [lo, hi]. Exits with lo == hi + 1.
# Use when the target may be ABSENT and you must report that.

def search_closed(a, target):
    lo, hi = 0, len(a) - 1
    while lo <= hi:                  # <= : the range is closed
        mid = lo + (hi - lo) // 2    # lower mid
        if a[mid] == target:
            return mid
        if a[mid] < target:
            lo = mid + 1                 # +1 : mid is excluded
        else:
            hi = mid - 1                 # -1 : mid is excluded
    return -1                        # absent; lo is the insert point


# ---------------------------------------------------------- Shape B
# Half-open [lo, hi). The answer is where the range collapses.
# "Smallest i such that predicate(i) is True."

def lower_bound(a, x):
    lo, hi = 0, len(a)           # hi is one PAST the end
    while lo < hi:               # < : the range is half-open
        mid = lo + (hi - lo) // 2    # lower mid
        if a[mid] >= x:
            hi = mid                 # mid may be the answer: keep it
        else:
            lo = mid + 1             # mid is not: exclude it
    return lo                    # lo == hi == the answer


# ---------------------------------------------------------- Shape C
# Shape B's mirror. "Largest x with feasible(x) True."
# The midpoint MUST round up: lo = mid has to make progress.

def largest_feasible(lo, hi, feasible):
    while lo < hi:
        mid = lo + (hi - lo + 1) // 2   # UPPER mid (lo = mid)
        if feasible(mid):
            lo = mid                    # mid may be the answer: keep it
        else:
            hi = mid - 1                # mid is not: exclude it
    return lo                    # the largest feasible value


# --------------------------------------------------- the one-line form
import bisect

def count_equal(a, x):
    """How many elements equal x? Two Shape-B calls."""
    return bisect.bisect_right(a, x) - bisect.bisect_left(a, x)

Why Shape B cannot return “not found”

This surprises people, so it is worth being explicit. Shape B narrows a half-open range until lo == hi, and returns lo. That value always exists — it is an index in [0, n]. When the target is absent, Shape B returns the insertion point, which is the index where the target would go to keep the array sorted. That is not a failure; it is extra information, and it is exactly what Search Insert Position (35) asks for.

So Shape B is strictly more informative than Shape A, and you should prefer it whenever the problem asks for a position rather than a yes/no. When the problem genuinely needs ‘not found’, compute the lower bound and then verify: i = bisect_left(a, x) and check i < len(a) and a[i] == x.

The reframing

Shape B never fails. It returns the insertion point, which is the answer to a different question than the one you thought you were asking.

The pairing rule, stated three ways

The infinite-loop bug always has the same cause: a branch that assigns mid to a bound without moving past it, combined with a midpoint that rounds the wrong way. Three equivalent statements of the fix:

  • By the branch: if a branch assigns lo = mid, use the upper mid. If a branch assigns hi = mid, use the lower mid.
  • By the loop: while lo < hi with hi = mid is the lower-mid shape. while lo < hi with lo = mid is the upper-mid shape. Never mix them.
  • By the symptom: if your search hangs, your midpoint rounds down and your lo branch does not advance. Add + 1 to the midpoint — do not add + 1 to lo = mid.

Choosing between the shapes in an interview

Say the following sentence out loud before you write code: the answer is either a value I am looking for, in which case I use the closed shape and check for absence; or it is the boundary where a monotone predicate flips, in which case I use the half-open shape and return the collapse point.

That sentence takes four seconds and it converts the most error-prone part of the interview into a decision you have already made.

The Problem

Given an array of integers nums which is sorted in ascending order, and an integer target, write a function to search target in nums. If target exists, then return its index. Otherwise, return -1.

You must write an algorithm with O(log n) runtime complexity.

Example 1:

Input: nums = [-1,0,3,5,9,12], target = 9
Output: 4

Explanation 9 exists in nums and its index is 4

Example 2:

Input: nums = [-1,0,3,5,9,12], target = 2
Output: -1

Explanation 2 does not exist in nums so return -1

Constraints:

  • 1 <= nums.length <= 104
  • -104 < nums[i], target < 104
  • All the integers in nums are unique.
  • nums is sorted in ascending order.
Signature
def search(nums, target):   # -> integer

In one lineReturn the index of target in a sorted array, or -1.

The insightThis is the pure Shape A. The only decision is that the range is closed, so the loop uses <= and both branches move past mid.

The closed range [lo, hi] contains the candidates. Each iteration examines mid and discards it by moving a bound past it. When lo > hi the range is empty and the target is absent.

The invariant to state: every index outside [lo, hi] has been ruled out. That is what justifies returning -1 at the end.

def search(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = lo + (hi - lo) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1

Complexity. O(log n) time, O(1) space. The loop runs at most ceil(log2(n + 1)) times.

Pitfall

Writing hi = mid instead of hi = mid - 1. With the lower midpoint this hangs on two-element ranges: lo = 0, hi = 1 gives mid = 0, and hi = 0 repeats forever.

Pitfall

Writing while lo < hi. That drops the last candidate and silently returns -1 for a single-element array.

Follow-up. “What if the array has duplicates and you want the first occurrence?” That is chapter 11 — bisect_left, which is Shape B with the predicate a[i] >= x.

You must write an algorithm with O(log n) runtime complexity.

Example 1:

Input: nums = [1,3,5,6], target = 5
Output: 2

Example 2:

Input: nums = [1,3,5,6], target = 2
Output: 1

Example 3:

Input: nums = [1,3,5,6], target = 7
Output: 4

  • -104 <= nums[i] <= 104
  • nums contains distinct values sorted in ascending order.

Signature
def searchInsert(nums, target):   # -> integer

In one lineReturn the index where target should be inserted to keep the array sorted.

The insightThis is Shape B with no modification at all. The insertion point is the collapse point of the half-open range.

Compare with 704: there, an absent target was a failure. Here it is the answer. The same search returns both.

bisect.bisect_left(nums, target) is the standard library version. Write the loop by hand in an interview, then mention that bisect_left does exactly this.

def search_insert(nums, target):
    lo, hi = 0, len(nums)              # half-open: hi may be len(nums)
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if nums[mid] >= target:        # predicate: a[mid] >= target
            hi = mid                   # mid may be the answer
        else:
            lo = mid + 1               # mid is not
    return lo                       # == bisect_left(nums, target)

Complexity. O(log n) time, O(1) space. Note hi starts at len(nums), which is why the range is half-open.

Pitfall

Starting hi = len(nums) - 1. Then a target larger than every element returns len(nums) - 1 instead of len(nums).

Pitfall

Using nums[mid] > target as the predicate. That computes bisect_right, which is off by one when duplicates exist.

Follow-up. “And if you want the position after all equal elements?” Change >= to >. The two functions differ by exactly one character — which is why count_equal in the template is a subtraction of two bisect calls rather than a custom loop.

LC 34  ·  Medium  ·  asked by 0 companies  ·  AC 49.7%  ·  Array, Binary Search
The Problem

Given an array of integers nums sorted in non-decreasing order, find the starting and ending position of a given target value.

If target is not found in the array, return [-1, -1].

You must write an algorithm with O(log n) runtime complexity.

Example 1:

Input: nums = [5,7,7,8,8,10], target = 8
Output: [3,4]

Example 2:

Input: nums = [5,7,7,8,8,10], target = 6
Output: [-1,-1]

Example 3:

Input: nums = [], target = 0
Output: [-1,-1]

Constraints:

  • 0 <= nums.length <= 105
  • -109 <= nums[i] <= 109
  • nums is a non-decreasing array.
  • -109 <= target <= 109
Signature
def searchRange(nums, target):   # -> integer[]

In one lineReturn [first, last] index of target, or [-1, -1].

The insightTwo Shape B calls with predicates >= and >. No custom binary search is needed, and no post-processing beyond one validity check.

first = bisect_left(a, x) is the smallest index with a[i] >= x. last = bisect_right(a, x) - 1 is the largest index with a[i] <= x.

The existence check is first < len(a) and a[first] == x. Without it, an absent target returns [n, n-1], which is nonsense that some test cases will catch.

from bisect import bisect_left, bisect_right

def search_range(nums, target):
    first = bisect_left(nums, target)     # smallest index, a[i] >= x
    if first == len(nums) or nums[first] != target:
        return [-1, -1]                   # absent; Shape B cannot tell
    last = bisect_right(nums, target) - 1 # largest index, a[i] <= x
    return [first, last]


# By hand, to show it is the same shape twice:
def search_range_manual(nums, target):
    def bound(x, strict):
        lo, hi = 0, len(nums)
        while lo < hi:
            mid = lo + (hi - lo) // 2
            if nums[mid] > x or (not strict and nums[mid] == x):
                hi = mid
            else:
                lo = mid + 1
        return lo
    first = bound(target, False)
    if first == len(nums) or nums[first] != target:
        return [-1, -1]
    return [first, bound(target, True) - 1]

Complexity. O(log n) time, O(1) space — two searches, so about twice the constant of 704.

Pitfall

Returning [first, bisect_right(nums, target)]. The right bound is exclusive, so it needs the - 1.

Pitfall

Skipping the validity check. [n, n-1] is not a valid answer and will fail the empty-result test.

Follow-up. “What if you must not use bisect?” Write bound once with a strict flag, as above. The flag is the only difference between the two calls.

You are a product manager and currently leading a team to develop a new product. Unfortunately, the latest version of your product fails the quality check. Since each version is developed based on the previous version, all the versions after a bad version are also bad.

Suppose you have n versions [1, 2, ..., n] and you want to find out the first bad one, which causes all the following ones to be bad.

You are given an API bool isBadVersion(version) which returns whether version is bad. Implement a function to find the first bad version. You should minimize the number of calls to the API.

Output: 4

call isBadVersion(5) -> true
call isBadVersion(4) -> true
Then 4 is the first bad version.

Example 2:

Input: n = 1, bad = 1
Output: 1

Constraints:

  • 1 <= bad <= n <= 231 - 1
Signature
def firstBadVersion(n, bad):   # -> integer

In one lineGiven isBadVersion(v), find the first bad version.

The insightThe predicate isBadVersion is monotone by construction (false, false, ..., true, true), so this is Shape B with no array at all.

This is the cleanest possible demonstration of the pattern: there is no data structure, only a monotone predicate. The search space is the version numbers, not an index into anything.

Set lo = 1, hi = n and let hi be inclusive of the answer candidate. while lo < hi with hi = mid and lo = mid + 1 converges on the first true.

def first_bad_version(n):
    lo, hi = 1, n
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if isBadVersion(mid):      # monotone predicate
            hi = mid               # mid may be the first bad one
        else:
            lo = mid + 1           # mid is definitely good
    return lo

Complexity. O(log n) calls to isBadVersion, O(1) space. The number of calls is the cost model here — say so, because the problem statement asks for it.

Pitfall

Using Shape A and a last_bad variable. That is O(n) in the worst case and misses the point of the exercise.

Pitfall

Writing hi = mid - 1. With hi inclusive of a candidate, subtracting 1 discards the answer.

Follow-up. “How many calls does your solution make?” ceil(log2 n). For n = 2^31 - 1 that is 31 calls. Being able to answer this precisely is worth as much as the code.

69Sqrt(x)
LC 69  ·  Easy  ·  asked by 7 companies  ·  AC 42.3%  ·  Math, Binary Search, Newton’s Method
The Problem

Given a non-negative integer x, return the square root ofxrounded down to the nearest integer. The returned integer should be non-negative as well.

You must not use any built-in exponent function or operator.

  • For example, do not use pow(x, 0.5) in c++ or x ** 0.5 in python.

Example 1:

Input: x = 4
Output: 2

Explanation The square root of 4 is 2, so we return 2.

Example 2:

Input: x = 8
Output: 2

Explanation The square root of 8 is 2.82842..., and since we round it down to the nearest integer, 2 is returned.

Constraints:

  • 0 <= x <= 231 - 1
Signature
def mySqrt(x):   # -> integer

In one lineInteger square root of x, rounded down.

The insightThis is Shape C — the largest feasible form — and it is the problem that exposes the midpoint rule.

The predicate is mid * mid <= x. It is monotone: if mid works, every smaller value works. So the answer is the largest feasible mid, which is Shape C.

Because the feasible branch assigns lo = mid, the midpoint must round up. If you use the lower midpoint here, lo = mid makes no progress on a two-element range and the loop hangs. This is the bug the whole chapter is about, in its purest form.

Note hi = x // 2 + 1 rather than x. For x >= 4 the answer is at most x // 2, so this halves the search range; the + 1 keeps x = 1 working.

def my_sqrt(x):
    if x < 2:
        return x
    lo, hi = 1, x // 2 + 1             # answer <= x // 2 for x >= 4
    while lo < hi:
        mid = lo + (hi - lo + 1) // 2  # UPPER mid: required by lo = mid
        if mid * mid <= x:             # feasible
            lo = mid                   # keep it; mid may be the answer
        else:
            hi = mid - 1               # discard it
    return lo


# Same thing without the midpoint trap; Shape B on first failure:
def my_sqrt_shapeb(x):
    lo, hi = 1, x // 2 + 1
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if mid * mid > x:              # "too big" is the predicate
            hi = mid
        else:
            lo = mid + 1
    return lo - 1                   # one before first too-big value

Complexity. O(log x) time, O(1) space. Newton’s method is faster in practice but is not the expected answer here.

Pitfall

Using the lower midpoint with lo = mid. Infinite loop. If you remember only one thing from this chapter, remember this line.

Pitfall

Forgetting the x < 2 guard. x = 0 gives hi = 1 and x = 1 gives hi = 1, both of which happen to work, but the guard makes it obvious rather than accidental.

Follow-up. “Can you avoid the midpoint rule entirely?” Yes — search for the first mid with mid * mid > x using Shape B and return lo - 1, as in my_sqrt_shapeb. Choosing the predicate so that Shape B applies is a legitimate way to dodge the upper midpoint, and offering it shows you understand the trade.

162Find Peak Element
LC 162  ·  Medium  ·  asked by 8 companies  ·  AC 47.2%  ·  Array, Binary Search
The Problem

A peak element is an element that is strictly greater than its neighbors.

Given a 0-indexed integer array nums, find a peak element, and return its index. If the array contains multiple peaks, return the index to any of the peaks.

You may imagine that nums[-1] = nums[n] = -∞. In other words, an element is always considered to be strictly greater than a neighbor that is outside the array.

You must write an algorithm that runs in O(log n) time.

Example 1:

Input: nums = [1,2,3,1]
Output: 2

Explanation 3 is a peak element and your function should return the index number 2.

Example 2:

Input: nums = [1,2,1,3,5,6,4]
Output: 5

Explanation Your function can return either index number 1 where the peak element is 2, or index number 5 where the peak element is 6.

Constraints:

  • 1 <= nums.length <= 1000
  • -231 <= nums[i] <= 231 - 1
  • nums[i] != nums[i + 1] for all valid i.
Signature
def findPeakElement(nums):   # -> integer

In one lineFind any peak element in an array where a[i] != a[i+1].

The insightThe array is not sorted, but the comparison with the right neighbour is a monotone predicate. Where the slope turns from up to down, there is a peak.

Define predicate(mid) = a[mid] > a[mid + 1]. If mid is on a downward slope, a peak exists at or to the left. If mid is on an upward slope, a peak exists at or to the right.

That makes the predicate monotone in the search sense — false, false, ..., true, true — so Shape B applies directly. hi starts at len(a) - 1 because mid + 1 must be in range.

This is the template for a whole family: binary search works whenever you can decide which half contains the answer, even if the array is not sorted.

def find_peak_element(nums):
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if nums[mid] > nums[mid + 1]:   # descending -> peak at or left
            hi = mid
        else:                           # ascending -> peak at or right
            lo = mid + 1
    return lo                            # a peak index

Complexity. O(log n) time, O(1) space. The problem asks for O(log n), which is the hint that this is a binary search despite the unsorted input.

Pitfall

Comparing with a[mid - 1] instead. Both work, but mixing the two comparisons across the two branches is how off-by-one bugs get in. Pick one reference and stay consistent.

Pitfall

Reading nums[mid + 1] when mid could be len(nums) - 1. With hi = len(nums) - 1 and the lower midpoint, mid < hi always holds, so mid + 1 is safe — but you must be able to say why.

Follow-up. “What if there are duplicates?” Find Peak Element II (1901) does it in 2-D. With duplicates in 1-D the predicate stops being monotone and you need Find Minimum in Rotated Sorted Array II (154)'s trick of shrinking both ends.

Signature
def search(nums, target):   # -> integer

In one lineSearch for target in a rotated sorted array with distinct values.

The insightExactly one of the two halves [lo, mid] and [mid, hi] is sorted. Find which, then ask whether the target lies inside that sorted half.

The array is not sorted, but it is piecewise monotone, and one piece always contains mid. The test a[lo] <= a[mid] tells you whether the left half is the sorted one.

If the left half is sorted, the target is in it exactly when a[lo] <= target < a[mid]; otherwise it must be in the right half. The two branches are mirror images.

This is Shape A with a two-step decision replacing the three-way comparison. The bounds still move past mid.

def search_rotated(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = lo + (hi - lo) // 2
        if nums[mid] == target:
            return mid
        if nums[lo] <= nums[mid]:        # left half [lo, mid] sorted
            if nums[lo] <= target < nums[mid]:
                hi = mid - 1             # target lies inside it
            else:
                lo = mid + 1             # so it is in the right half
        else:                            # right half [mid, hi] sorted
            if nums[mid] < target <= nums[hi]:
                lo = mid + 1             # target lies inside it
            else:
                hi = mid - 1             # so it is in the left half

Pitfall

Using nums[lo] < nums[mid] instead of <=. With two elements lo == mid, and the strict comparison misclassifies the half.

Pitfall

Pitfall

def find_min(nums):

    while lo < hi:
        mid = lo + (hi - lo) // 2
        if nums[mid] < nums[hi]:      # right half is sorted
            hi = mid                  # minimum is at or left of mid
        else:                         # minimum is strictly right of mid
            lo = mid + 1
    return nums[lo]

In one lineIn a sorted array where every element appears twice except one, find the single element.

The insightBinary search on the parity of the index. Before the single element, pairs start at even indices; after it, at odd indices. The index XOR trick makes the pair test one expression.

For any index i, its pair partner is i ^ 1. Before the single element, a[i] == a[i ^ 1] holds for every i; after it, the parity is flipped and the equality fails.

So the predicate a[mid] == a[mid ^ 1] is monotone: true, true, ..., false, false. Shape B finds the first false.

mid must be even for the test to mean what you think. mid -= mid % 2 forces that, and it is the line that makes the solution robust rather than lucky.

def single_non_duplicate(nums):
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        mid = lo + (hi - lo) // 2
        mid -= mid % 2                 # force mid to be even
        if nums[mid] == nums[mid + 1]: # pair intact -> single right
            lo = mid + 2
        else:                          # broken pair -> single at or left
            hi = mid
    return nums[lo]

Complexity. O(log n) time, O(1) space. The XOR form mid ^ 1 is equivalent and slightly more elegant; both are accepted.

Pitfall

Advancing lo = mid + 1. Because pairs move in steps of two, the correct advance is mid + 2 — a + 1 leaves lo pointing at the second half of a pair.

Pitfall

Forgetting the mid -= mid % 2 normalisation. On odd mid the comparison tests the wrong pair and the search goes to the wrong half.

def search_matrix(matrix, target):

    lo, hi = 0, m * n - 1
    while lo <= hi:

        if matrix[row][col] < target:

Two Pointers – Converging

The Kernel

One pointer at each end, both moving inward. Every problem here is the same while l < r: loop; only the move rule and the update rule differ.

This is the cheapest pattern in the book. There is one loop, two pointers, and a rule that says which one moves. Once the array is sorted, a pair is no longer something you search for — it is something you walk toward, and the walk is O(n) instead of O(n&sup2;).

The reason it works is a monotonicity argument, and you should be able to state it out loud in an interview. Put the smallest element on the left and the largest on the right. If their sum is too small, then the smallest element cannot be part of any valid pair — it is too small to pair with anything, including the largest value available. So discard it and move on. If the sum is too large, by the same argument the largest element cannot be in any valid pair. Every iteration removes one candidate permanently, which is what makes a single linear pass enough.

Everything else — 3Sum, 4Sum, closest pair, container with most water, palindrome checking — is that argument wearing a different costume. The chapter is short because there is genuinely only one idea in it.

The Boundary Rules

Seven rules. Rule 1 and rule 2 are the loop itself; rule 3 is the precondition that makes the loop valid; rules 4 through 7 are the traps that separate a working answer from an accepted one.

  1. Loop condition is always while l < r (never <=) — a converging pair must have two distinct indices.
  2. Move exactly one pointer per iteration, decided by a comparison against the target. Moving both is the classic bug that silently skips candidates.
  3. If the array is not sorted and the problem is about pairs/triplets, sort first — the O(n log n) sort is what buys you the O(n) scan.
  4. After sorting, the index you get back is an index into the sorted array. If the problem asks for original indices, you must carry them.
  5. Dedup rule: skip a value only when it equals the previous kept value, and only while l < r. if l > start and a[l] == a[l-1]: continue.
  6. 3Sum is for i in range(n-2) wrapping a converging pair; the outer loop carries its own dedup and its own early exit if a[i] > 0: break.
  7. Container-with-most-water never needs sorting: the greedy move is move the shorter side, because the shorter side is the bottleneck.

The Template

There is one frame and one shell. The frame is the converging loop. The shell is the deduplication wrapper you need whenever the problem asks for a set of tuples rather than a single pair, which is where most submissions fail.

Memorise the frame. The shell you can rebuild each time from rule 5, as long as you remember that duplicates are skipped at the anchor and at the pointer separately — they are two different loops and they are both required.

# ------------------------------------------------- the frame
# Sorted array, one pointer at each end, both moving inward.

def two_sum_sorted(a, target):
    l, r = 0, len(a) - 1
    while l < r:            # never <= : a pair needs two indices
        s = a[l] + a[r]
        if s == target:
            return [l, r]
        if s < target:
            l += 1              # too small: low side is the bottleneck
        else:
            r -= 1              # too large: high side is the bottleneck
    return []               # no pair exists


# --------------------------------------------- the dedup shell
# Use whenever the answer is a SET of tuples, not one pair.

def three_sum(a):
    a.sort()                # sorting is what buys the O(n) scan
    out = []
    for i in range(len(a) - 2):
        if a[i] > 0:
            break           # sorted: no later triple can reach 0
        if i > 0 and a[i] == a[i - 1]:
            continue        # skip a duplicate ANCHOR
        l, r = i + 1, len(a) - 1
        while l < r:
            s = a[i] + a[l] + a[r]
            if s == 0:
                out.append([a[i], a[l], a[r]])
                l += 1
                while l < r and a[l] == a[l - 1]:
                    l += 1  # skip duplicates of the value just used
            elif s < 0:
                l += 1
            else:
                r -= 1
    return out

Why moving both pointers at once is wrong

It is tempting to think that when the sum is too small you should advance l and retreat r, since neither endpoint looked right. That is a bug, and it is a silent one: it skips candidates without ever failing a test you would notice on a small example.

The monotonicity argument is what tells you the truth. When a[l] + a[r] is too small, a[l] is too small to pair with a[r] — the largest remaining value. That tells you nothing about a[r]. a[r] may well be the correct partner for some other element further in. Moving r discards it on no evidence.

So the rule is mechanical: exactly one pointer moves per iteration, and the comparison decides which. If you find yourself writing both, you have lost the invariant and the linear bound with it.

The two deduplication loops are not the same loop

In the three_sum shell there are two places duplicates are skipped, and they exist for different reasons. The outer check if i > 0 and a[i] == a[i - 1]: continue skips a repeated anchor — if you have already produced every triple starting with the value 2, starting again at another 2 produces the same set.

The inner loop after a hit skips repeated partners — once you have emitted [-4, 2, 2], advancing l onto a second 2 would emit it again.

The trap is that the inner loop must be guarded by l < r, not by a fixed bound. Without it, a long run of equal values can walk l past r and produce a pair that reuses the same element twice, which is not a pair at all.

The insightSame frame, but the pointers must skip characters that do not count, and the skip loops need the same l < r guard as the outer loop.

The frame compares s[l] with s[r] and moves both inward — note that this is one of the few places both pointers move, because a palindrome match consumes both ends at once.

The new ingredient is the inner skip loops. A character that is not alphanumeric is invisible to the problem, so each pointer walks over it. The subtlety is that these loops must be guarded by l < r themselves. Without the guard, a string like ".," walks l off the end of the string and the next comparison reads out of range.

def isPalindrome(s):
    l, r = 0, len(s) - 1
    while l < r:
        while l < r and not s[l].isalnum():
            l += 1
        while l < r and not s[r].isalnum():
            r -= 1
        if s[l].lower() != s[r].lower():
            return False
        l += 1
        r -= 1
    return True

Output: []

Explanation The only possible triplet does not sum up to 0.

Example 3:

Explanation The only possible triplet sums up to 0.

  • 3 <= nums.length <= 3000
  • -105 <= nums[i] <= 105
Signature
def threeSum(nums):   # -> list<list<integer>>

In one lineReturn every triple of distinct positions whose values sum to zero, with no repeated triples.

The insightSort, then wrap the converging frame in a loop over the anchor. The whole difficulty is the two deduplication loops, not the search.

Sorting does two things at once: it makes the inner converging scan valid, and it makes duplicates adjacent, which is what makes them skippable at all. Without the sort you cannot dedup in O(1) space per candidate.

The outer loop fixes nums[i] as the anchor and asks the inner frame for a pair summing to -nums[i]. Two early exits matter. if nums[i] > 0: break is valid because once the anchor is positive, every later anchor is larger and no triple can reach zero. The duplicate-anchor check if i > 0 and nums[i] == nums[i - 1]: continue is what stops the same triple being emitted from different starting positions.

After a hit, l must skip past equal values. This is the second dedup loop, and it is guarded by l < r so it cannot overrun.

def threeSum(nums):
    nums.sort()
    out = []
    for i in range(len(nums) - 2):
        if nums[i] > 0:
            break                    # sorted: no later triple reaches 0
        if i > 0 and nums[i] == nums[i - 1]:
            continue                 # duplicate anchor
        l, r = i + 1, len(nums) - 1
        while l < r:
            s = nums[i] + nums[l] + nums[r]
            if s == 0:
                out.append([nums[i], nums[l], nums[r]])
                l += 1
                while l < r and nums[l] == nums[l - 1]:
                    l += 1           # duplicate partner
            elif s < 0:
                l += 1
            else:
                r -= 1
    return out

Complexity. O(n&sup2;) time — O(n log n) to sort plus O(n) for each of n anchors. O(1) extra space beyond the output.

Pitfall

Keeping only one of the two dedup checks. With only the anchor check, a triple like [-1, 0, 1] is emitted once per duplicate partner; with only the partner check, it is emitted once per duplicate anchor.

Pitfall

Using a set of tuples instead of the two loops. It works, but it hides whether you understand the invariant, and interviewers ask.

Pitfall

Dropping the l < r guard inside the partner skip loop, which lets l run past r and reuse an element twice.

Follow-up. “And 4Sum?” Add a second anchor loop around the same shell — O(n&sup3;). The pattern does not change; only the nesting does.

  • 2 <= n <= 105
  • 0 <= height[i] <= 104
Signature

In one lineGiven vertical lines at each index, choose two that with the x-axis hold the most water.

The insightThe only problem in the chapter that must not be sorted, because the answer depends on the original positions. The move rule is different too: move the shorter side.

The area is min(height[l], height[r]) * (r - l). Sorting would destroy the widths, so the array stays as it is and the frame runs on the original indices.

The move rule follows from the bottleneck argument. The shorter wall caps the area. Moving the taller wall inward can only reduce the width while the cap stays the same, so it can never improve. Moving the shorter wall is the only move that has any chance of finding a larger cap. This is the same “discard the endpoint that cannot participate” argument as the sorted case, applied to a different monotonicity.

Note what you do not do: you never look ahead. The greedy move is locally justified and globally optimal here, and the proof is the bottleneck argument above.

def maxArea(height):
    l, r = 0, len(height) - 1
    best = 0
    while l < r:
        h = min(height[l], height[r])
        best = max(best, h * (r - l))
        if height[l] < height[r]:
            l += 1          # the shorter wall is the bottleneck
        else:
            r -= 1
    return best

Complexity. O(n) time, O(1) space. One comparison and one move per iteration.

Pitfall

Sorting the array first. The area depends on index distance, so sorting changes the answer — this is the trap that catches people who have just learned 3Sum.

Pitfall

Moving the taller wall. It looks harmless and is wrong on inputs where the optimum needs both walls from one half.

Pitfall

Computing h * (r - l) with h = height[l] only, instead of the minimum of the two.

Follow-up. “Prove the greedy move.” This is the standard exchange argument: any solution that keeps the shorter wall and discards the taller one is dominated by the move the algorithm makes.

In one lineFind the triple whose sum is closest to a target.

The insightThe 3Sum shell with the equality test replaced by a running best. No deduplication is needed, because the answer is a single number rather than a set of tuples.

This is the clearest demonstration that the two dedup loops in 3Sum are not part of the frame — they belong to the output shape. Here the output is one integer, so both loops vanish and the code gets shorter.

The frame is unchanged: too small advances l, too large retreats r. The only addition is that every candidate is compared against the best so far, since the exact target may never be hit.

The early return when s == target is worth keeping: an exact hit is optimal and no further work can improve it.

def threeSumClosest(nums, target):
    nums.sort()
    best = nums[0] + nums[1] + nums[2]
    for i in range(len(nums) - 2):
        l, r = i + 1, len(nums) - 1
        while l < r:
            s = nums[i] + nums[l] + nums[r]
            if abs(s - target) < abs(best - target):
                best = s
            if s < target:
                l += 1
            elif s > target:
                r -= 1
            else:
                return target        # exact hit: cannot be beaten
    return best

Input: height = [4,2,0,3,2,5]
Output: 9

Constraints:

  • n == height.length
  • 1 <= n <= 2 * 104
  • 0 <= height[i] <= 105
Signature
def trap(height):   # -> integer

In one lineGiven an elevation map, compute how much rain it traps.

The insightThe hardest problem in the chapter, and it is still the same frame. The water above any bar is min(left_max, right_max) - height, and the converging scan can supply that minimum without ever building either array.

The straightforward solution computes two prefix arrays — the tallest bar to the left of each index and the tallest to the right — then sums min(left, right) - height. That is O(n) time and O(n) space, and it is a perfectly good answer.

The two-pointer version removes the arrays. The key observation: when height[l] < height[r], the water above l is determined entirely by left_max, because there is a bar at r at least as tall as height[l] somewhere to the right, which is enough to guarantee right_max >= height[l]. So min(left_max, right_max) == left_max and you can settle l immediately without knowing right_max at all.

That is the whole trick, and it is worth stating precisely: you never need both maxima, only the one on the side of the shorter bar. The loop advances whichever side is shorter and settles that index permanently.

def trap(height):
    if not height:
        return 0
    l, r = 0, len(height) - 1
    left_max = right_max = 0
    water = 0
    while l < r:
        if height[l] < height[r]:
            left_max = max(left_max, height[l])
            water += left_max - height[l]
            l += 1
        else:
            right_max = max(right_max, height[r])
            water += right_max - height[r]
            r -= 1
    return water

Complexity. O(n) time, O(1) space. Strictly better than the prefix-array solution on memory, and the version an interviewer is hoping you reach.

Pitfall

Comparing height[l] with height[r] and then using the wrong maximum. The rule is: whichever bar is shorter, its side’s maximum is the binding constraint. Swap them and the answer is wrong on asymmetric inputs.

Pitfall

Updating left_max after accumulating instead of before, which adds a negative term at every new maximum.

Pitfall

Forgetting the empty-input guard, which makes l and r invalid on an empty array.

Follow-up. “What about the 2-D version?” Problem 407. It needs a heap rather than two pointers — see chapter 32 — because there is no single pair of maxima that bounds the water.

Constraints:

  • 1 <= s.length <= 105
  • s consists of lowercase English letters.
Signature
def validPalindrome(s):   # -> boolean

In one lineDecide whether a string is a palindrome after deleting at most one character.

The insightRun the frame; at the first mismatch, the answer is the OR of the two possible deletions. Only one branch can be right, and you must try both.

The frame advances while the characters match. The moment they differ, exactly one of two things must be true: the left character is the extra one, or the right character is. So you check the remaining substring both ways and accept if either works.

The trap is thinking you can decide which one to delete from the local comparison. You cannot. Given "abca" mismatching at the outer pair, both branches must be tested, because the surrounding context decides it and you have not looked at the surroundings yet.

Factor the plain check into a helper. The outer loop runs once and calls the helper at most twice, which is why the total work is still linear — each helper call scans a substring, and there are only two of them.

def validPalindrome(s):
    def ok(i, j):
        while i < j:
            if s[i] != s[j]:
                return False
            i += 1
            j -= 1
        return True

    l, r = 0, len(s) - 1
    while l < r:
        if s[l] != s[r]:
            return ok(l + 1, r) or ok(l, r - 1)
        l += 1
        r -= 1
    return True

Complexity. O(n) time — the outer loop plus at most two linear scans. O(1) space beyond the recursion-free helper.

Pitfall

Trying only one branch, e.g. always skipping s[l]. Which character is the extra one depends on the rest of the string, not on the mismatch itself.

Pitfall

Recursing instead of using a helper and accidentally making it exponential, because each mismatch can spawn two more.

Pitfall

Returning False after both branches fail but forgetting that the loop must also return True when no mismatch is found at all.

Follow-up. “At most k deletions?” That is the two-sequence DP of chapter 62 — the greedy two-branch trick works only for k = 1.

Signature
def sortedSquares(nums):   # -> integer[]

In one lineGiven a sorted array, return the squares of its elements in sorted order.

The insightThe largest square is at one of the two ends, so fill the output from the back while converging inward.

The array is sorted, but its squares are not: a large negative number at the left can square to more than a large positive at the right. So the usual “smallest first” order is broken.

The fix is to reverse the direction of the fill. The largest square is always at one of the two ends, because that is where the largest magnitudes live. Compare abs(nums[l]) with abs(nums[r]), take the bigger square, place it at the current back position, and advance that pointer. The output fills from the last index down to zero.

Note that both pointers move inward but only one per iteration, exactly as rule 2 requires. Writing into a preallocated list from the back avoids the insert(0, ...) that would make the solution quadratic.

def sortedSquares(nums):
    n = len(nums)
    out = [0] * n
    l, r = 0, n - 1
    for k in range(n - 1, -1, -1):
        if abs(nums[l]) > abs(nums[r]):
            out[k] = nums[l] * nums[l]
            l += 1
        else:
            out[k] = nums[r] * nums[r]
            r -= 1
    return out

Complexity. O(n) time, O(n) space for the output. Beats the obvious sort-the-squares approach, which is O(n log n).

Pitfall

Using nums[l] nums[l] > nums[r] nums[r] without abs. The squares of negatives compare wrongly if you forget.

Pitfall

Writing to the front with out.append(...) and then reversing, which is correct but obscures the direction of the fill.

Pitfall

Using insert(0, x), which is O(n) per call and quietly turns a linear solution into a quadratic one.

Follow-up. “Why is the maximum always at an end?” Because x&sup2; is monotone in |x|, and the extremes of |x| are at the ends of a sorted array.
